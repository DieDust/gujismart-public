# 04 文库组织与文件夹标签

## 1. 本章结论

GujiSmart 当前已经具备多层文件夹、文件夹拖放排序、未分类视图、文件夹内容分页、批量加入/移动文献、标签分组、元数据自动标签、文库侧栏计数缓存和启动 AI 重分类等完整功能。文库主视图近期已经改为分页加载，文件夹内容也提供了 `limit/offset/has_more`，因此不需要推翻现有交互或迁移现有 SQLite 数据。

当前主要风险在于组织关系的写入约束不统一，以及若干“看似读取或轻量刷新”的路径仍会执行全库写入或全库物化：`folders:update` 可以绕过移动接口的循环校验；同名文件夹更新会直接合并并删除来源文件夹；`tags:list` 每次读取都会宽松合并和删除标签；文件夹累计计数会把全部文献关系复制到多个内存 `Set`；文件夹总览为了每个文件夹最多 6 条预览却先读取全部关系。这些行为在小库中不明显，但与“文献数量逻辑上无限、内存与并发有界”的产品约束冲突。

本章建议保留现有 `folders`、`document_folders`、`tags`、`document_tags` 和 `library_state_cache`，先把所有组织写入收口为显式命令，把读取接口变为纯读取，再将计数、扫描、标签重建和 AI 重分类改成可分页、可取消、可恢复的持久化任务。第一阶段不要求数据库迁移，也不要求新增依赖。

## 3. 当前数据流

### 3.1 文库列表与侧栏

```text
LibraryView
  -> library:getStateCache 读取侧栏快照
  -> folders:list + tags:list 读取组织项
  -> documents:listPage 按 10/50/100 篇分页读取文献
  -> 文件夹筛选先在 renderer 展开全部后代 ID
  -> 文献增删或组织关系变化后把 library_state_cache 标脏
  -> 主进程延迟 1.5 秒同步重算全部智能视图、文件夹和标签计数
```

文库文献列表已经具有分页、加载更多、已加载数量和“全选已加载”的语义，这是可继续沿用的正确基础。问题主要位于组织元数据和计数刷新，而不是主列表分页本身。

### 3.2 文件夹总览与内容

```text
FoldersView
  -> folders:getOverview
     -> 读取全部文件夹
     -> 读取全部文献-文件夹关系并构造累计计数
     -> 读取全部关系对应的文献预览行
     -> 在 JS 中向祖先合并并截取每个文件夹最近 6 篇
  -> folders:getContent
     -> 当前文件夹直接文献按 limit/offset 分页
  -> 用户按需“加载更多”
```

`folders:getContent` 已限制单页 1 至 240 条。当前总览仍与全库关系规模线性增长，并且在多个祖先层级复制文献 ID 集合。

### 3.3 文件夹写入

```text
新建/编辑/拖放
  -> folders:create / folders:update / folders:move
  -> SQLite folders
  -> markLibraryStateCacheDirty()
  -> 延迟重算侧栏快照

批量加入/移动
  -> folders:addDocuments / folders:moveDocuments
  -> document_folders
  -> 保存数据库并刷新文库状态
```

拖放使用 `folders:move`，后端会阻止移动到自身或后代。编辑弹窗使用 `folders:update`，该接口直接允许更新 `parent_id`，没有复用同一校验；同名冲突还会自动执行递归合并。

### 3.4 标签与元数据标签

```text
TagsView / LibraryView
  -> tags:list
  -> refreshTagUsage()
     -> 全量重算 usage_count
     -> 宽松归一化合并重复标签
     -> 再次全量重算
     -> 删除未使用的生成标签
     -> 保存数据库
  -> 返回全部标签

OCR/元数据更新
  -> syncDocumentMetadataTags
  -> 写 document_tags
  -> 刷新标签使用数
```

标签管理页的文献选择器一次只请求 1000 篇文献；标签本身没有分页。自动标签重建会先把全部候选文献读取到数组中，所谓批次只是在处理固定数量后让出事件循环，并不限制内存或提供恢复游标。

### 3.5 启动 AI 重分类

启动时若配置了 LLM 且旧分类候选不超过 200 篇，会以 1 至 6 并发重新分类。候选超过 200 篇时整批跳过；小批任务即使部分失败，最终也把版本状态写成 `completed`，后续启动不会自动重试失败项。

## 4. 关键问题

### D04-P1-01 `folders:update` 绕过后端移动不变量，可制造循环文件夹关系

**证据等级：已确认。**

`folders:move` 会调用 `assertFolderMoveAllowed`，检查目标是否为自己或后代（`src/main/ipc/folders.ts:173` 至 `src/main/ipc/folders.ts:187`）。但 `folders:update` 直接把 `parent_id` 放进允许字段并执行 `UPDATE`（`src/main/ipc/folders.ts:633` 至 `src/main/ipc/folders.ts:675`），没有复用上述校验。

renderer 的编辑弹窗会提交 `name` 和 `parent_id`，前端过滤只能改善正常操作，不能替代进程边界校验。出现循环后，`buildFolderTree` 可能让整个循环分量从根节点消失，`collectFolderDescendantIds` 没有 visited 集合而可能无限递归，`isFolderDescendant` 也可能无限循环（`src/renderer/src/utils/folders.ts:14` 至 `src/renderer/src/utils/folders.ts:82`）。

**落实方案：**

1. 建立唯一的 `validateFolderParentChange(folderId, nextParentId)`，由 `create`、`update`、`move`、导入恢复和后续批量命令共同调用。
2. 后端在同一事务内读取目标和后代关系、校验、更新并重排，避免校验与写入之间被其他操作改变。
3. renderer 的树构建、后代收集和祖先查找仍加入 visited 保护；遇到循环时返回带 `corruptFolderIds` 的诊断结果，不能静默隐藏或卡死。
4. 为旧库提供“只检测”和“预演修复”：默认不自动改父级；用户确认后把循环中最晚更新的节点移到根级，并记录恢复报告。
5. 保留现有 IPC 名称和数据表，第一阶段零迁移。

### D04-P1-02 `tags:list` 是会合并、改写和删除用户数据的读取接口

**证据等级：已确认。**

`tags:list` 在任何查询前调用 `refreshTagUsage()`（`src/main/ipc/tags.ts:13` 至 `src/main/ipc/tags.ts:23`）。该函数会全量更新使用数、调用 `autoMergeDuplicateTags`、再次更新并删除未使用的生成标签（`src/main/database.ts:2426` 至 `src/main/database.ts:2433`）。自动合并使用宽松名称键，将关系迁移到保留标签后删除重复标签 ID（`src/main/database.ts:1328` 至 `src/main/database.ts:1369`）。

因此打开标签页、文库页或刷新列表都可能改变数据库。宽松归一化适合生成“可能重复”的候选，不适合在读取时替用户作不可见的语义决定；标签 ID 被删除还会让工作区缓存、外部引用或未来同步日志难以解释。

**落实方案：**

- `tags:list` 改为纯查询，使用 SQL 聚合实时返回当前页使用数，或读取增量维护的计数；禁止调用保存和清理函数。
- 标签去重改为显式 `tags:previewMerge` 和 `tags:merge` 两阶段命令，预览名称、来源、关系数、父子关系和保留 ID。
- 自动生成标签只允许在创建、解绑或维护任务中清理；清理任务先列出候选并支持撤销窗口。
- 精确重复可在写入时以明确的规范化键阻止；繁简、别名、异体字和同义词只建立 alias，不自动合并实体。
- 新增回归：调用 `listTags` 前后比较 `tags`、`document_tags`、数据库写入计数和文件修改时间，必须完全不变。

### D04-P1-03 编辑同名文件夹会静默递归合并并删除来源文件夹

**证据等级：已确认。**

`folders:update` 如果在目标父级找到同名文件夹，会直接调用 `mergeFolderInto` 并返回成功（`src/main/ipc/folders.ts:639` 至 `src/main/ipc/folders.ts:646`）。合并会迁移文献、递归迁移或继续合并子文件夹，最后删除来源文件夹（`src/main/ipc/folders.ts:111` 至 `src/main/ipc/folders.ts:160`）。编辑界面只执行普通保存，没有展示合并预览或二次确认。

**落实方案：**

- `folders:update` 只负责非破坏性编辑；遇到同层同名时返回稳定冲突码和目标 ID，不做任何写入。
- 新增显式 `folders:previewMerge` 和 `folders:merge`，预览重复文献、同名子文件夹、外部路径冲突、颜色/图标决策和最终保留 ID。
- 合并在单事务内完成，记录可撤销映射；至少在当前会话内提供撤销，长期撤销可复用模块 11 的操作日志设计。
- 新建同名文件夹也应明确返回 `alreadyExists`，不能把“新建成功”和“返回旧对象”混为一个状态。

### D04-P1-04 累计文件夹计数和文库状态刷新会在主进程物化全库关系并向祖先复制集合

**证据等级：已确认。**

`buildCumulativeFolderDocumentCounts` 读取全部文件夹和全部文献-文件夹关系，为每个文件夹建立文献 ID `Set`，再把每个子树的集合逐层并入祖先（`src/main/folder-scope.ts:47` 至 `src/main/folder-scope.ts:79`）。同一文献位于深层文件夹时会出现在多个祖先集合中，内存可能接近“关系数乘树深度”。

该函数被文件夹列表、总览和文库状态缓存调用。任何组织关系变化都会把缓存标脏，并在主进程延迟 1.5 秒同步执行完整重算（`src/main/library-state-cache.ts:91` 至 `src/main/library-state-cache.ts:103`、`src/main/library-state-cache.ts:241`、`src/main/library-state-cache.ts:319` 至 `src/main/library-state-cache.ts:368`）。

**落实方案：**

- 使用 SQLite 递归 CTE 和 `COUNT(DISTINCT doc_id)` 在数据库侧聚合，主进程只接收每个文件夹一个计数，不接收全库 ID 集合。
- 将状态重算放入单一后台 worker/job；renderer 读取上一个一致快照和 `refreshing/version`，不能由读取请求同步触发重算。
- 文件夹/标签关系写入后优先增量更新受影响祖先；夜间或空闲校准执行全量聚合并比较差异。
- 计数任务按数据库版本去重，短时间内大量写入只保留一个待运行版本。
- 在旧数据库上继续使用现有 `library_state_cache`；增量日志若确需新表，必须先证明 settings 快照无法满足恢复，再按模块 11 的备份与回滚规范审批迁移。

### D04-P1-05 文件夹总览为了每个文件夹最多 6 条预览，先读取全部文献关系

**证据等级：已确认。**

`buildFolderOverview` 查询所有 `document_folders` 关系及文献字段，并为每行执行首张页面图片相关子查询（`src/main/ipc/folders.ts:314` 至 `src/main/ipc/folders.ts:370`）。之后才在内存中按文件夹和后代合并并截取 6 条（`src/main/ipc/folders.ts:372` 至 `src/main/ipc/folders.ts:399`）。文库越大，返回前的临时数组、对象和文件授权路径越大，但用户实际只看少量卡片。

**落实方案：**

- `folders:getOverview` 只返回文件夹元数据和聚合计数，不附带全部预览来源。
- 新增有界 `folders:getPreview({ folderId, limit: 6 })`，只在卡片进入视口或用户展开时请求。
- 预览 SQL 使用已知 folderId 的后代递归 CTE、稳定排序和 `LIMIT`，只返回所需字段；首图路径使用已存在索引或预先保存的缩略图字段。
- renderer 对可见卡片限制并发并缓存版本，滚出视口后不保留原图对象。
- 旧 `recent_documents` 字段在一个兼容版本内保留为空或按需填充，等所有 renderer 调用迁移后再移除。

### D04-P1-06 外部文件夹扫描在主进程同步递归，缺少进度、取消和目录循环治理

**证据等级：已确认。**

`collectSupportedFolderFiles` 使用 `readdirSync`、`statSync` 和递归数组拼接遍历整个目录（`src/main/ipc/folders.ts:571` 至 `src/main/ipc/folders.ts:590`）；两个 IPC 直接在主进程调用并一次性返回全部结果（`src/main/ipc/folders.ts:756` 至 `src/main/ipc/folders.ts:779`）。`statSync` 会跟随符号链接或 Windows junction，代码没有真实路径 visited 集合、最大打开目录数、取消或部分结果协议。

**落实方案：**

- 扫描改为持久化 job：`queued/running/paused/completed/failed/cancelled`，以目录游标和批次保存进度。
- 在 worker 中使用异步目录迭代，记录规范化 realpath 与文件标识；发现链接、junction 或重复目录时按设置跳过并报告。
- renderer 订阅发现数量、已扫描目录、错误数和当前路径；用户可暂停、取消、继续，并在扫描完成前逐批确认导入。
- 单个权限错误作为条目错误继续扫描；根目录不可读才失败。空目录与扫描失败必须是不同状态。
- 结果不一次性返回全部路径；按游标分页读取，导入队列按用户设置的并发量慢慢消费。

### D04-P1-07 旧文件夹文献 API、标签选择器和部分批量命令仍有无界或静默上限

**证据等级：已确认。**

- `folders:getDocuments` 展开全部后代 ID，构造单个无界 `IN (...)` 并返回全部文献，没有分页（`src/main/ipc/folders.ts:734` 至 `src/main/ipc/folders.ts:745`）。
- `folders:moveDocuments` 对全部文献 ID 构造一个 `IN (...)` 删除，可能超过 SQLite 参数上限（`src/main/ipc/folders.ts:540` 至 `src/main/ipc/folders.ts:568`）。
- 标签页文献选择器固定请求 `limit: 1000`，UI 没有说明剩余文献不可见（`src/renderer/src/views/TagsView.tsx:113` 至 `src/renderer/src/views/TagsView.tsx:124`）。
- `tags:list` 返回全部标签，`tags:addDocuments` 对文献与标签做无界笛卡尔循环（`src/main/ipc/tags.ts:13` 至 `src/main/ipc/tags.ts:23`、`src/main/ipc/tags.ts:113` 至 `src/main/ipc/tags.ts:140`）。

**落实方案：**

- 将 `getFolderDocuments` 标记为兼容接口，内部使用游标分批或只允许小型调用；新调用统一使用 `getFolderContent`/`listDocumentsPage`。
- 标签列表和文献选择器加入搜索加游标分页；选择状态保存 ID，不依赖当前页对象。
- 大批量加入、移除和移动转为持久化批处理任务，按 100 至 500 条参数块执行；具体块大小通过基准确定。
- 所有 `IN (...)` 使用统一 chunk helper 或临时表/JSON table 方案，不能直接展开用户规模数组。
- UI 明确区分“全选当前页”“全选已加载”“选择当前筛选的全部 N 项”；最后一种使用服务端 selection token，不把全部 ID 发到 renderer。

### D04-P1-08 元数据标签重建一次性读取全部候选，批次只让出事件循环

**证据等级：已确认。**

`rebuildMetadataTagBindings` 先把全部候选文献读入 `documents` 数组，再逐篇执行多次查询和写入；`batchSize` 只控制每多少篇 `yieldToEventLoop()`（`src/main/metadata-tags.ts:539` 至 `src/main/metadata-tags.ts:587`）。任务没有 job ID、游标、取消、heartbeat 或重启恢复，最终才统一刷新使用数和保存。

**落实方案：**

- 按稳定 `(updated_at, id)` 或 rowid 游标读取固定批次，批次事务提交后保存游标、统计和失败 ID。
- 与标签人工编辑共享写入协调器；人工改名、合并或删除优先，后台任务在版本变化后重读目标。
- 单篇失败不终止整批，失败项可分页查看和单独重试；重复执行必须幂等。
- 进度展示“已扫描/已更新/跳过/失败”，不能用已加载数组长度估算全库总量。
- 在模块 02/03 的统一 `task_jobs/task_items` 调度器落地前，可把单个维护任务快照暂存在现有 settings JSON 作为兼容桥；最终必须迁入统一任务模型，不能为元数据标签另建第二套物理 job 表。

### D04-P1-09 启动 AI 重分类对大库永久跳过，小库部分失败仍标记完成

**证据等级：已确认。**

候选查询最多返回 201 条；超过 200 条时只记录跳过时间并返回（`src/main/metadata-reclassifier.ts:47` 至 `src/main/metadata-reclassifier.ts:90`），因此每次启动都可能重复跳过而没有处理入口。任务对单篇失败只累计 `failedCount`，所有 worker 结束后无条件把版本写为 `completed`（`src/main/metadata-reclassifier.ts:99` 至 `src/main/metadata-reclassifier.ts:160`）。

此外该行为只要发现数据库中有 LLM Key 就在启动后自动上传 OCR 文本，用户授权边界需与模块 07 一起收紧。

**落实方案：**

- 取消“候选超过阈值就整批跳过”，改为持久化排队、用户设置并发、每批有界处理；文献总量不设上限。
- 默认不在启动时自动发送内容。首次运行、服务商变化和隐私模式变化都必须取得明确授权。
- `completed` 只表示全部成功或被用户明确跳过；有失败时状态为 `partial_failed`，保留失败游标和重试入口。
- 模型、服务商、提示词版本和输入哈希写入每条结果；内容改变后旧分类标记为 stale。
- 无 API Key、离线或限流时任务保持可恢复等待，不反复弹错或丢失。

### D04-P2-01 标签父级写入没有循环、不存在目标和同层冲突校验

**证据等级：已确认；当前 UI 暴露程度有限。**

`tags:update` 对 `parent_id` 直接赋值（`src/main/ipc/tags.ts:42` 至 `src/main/ipc/tags.ts:79`），没有校验父标签存在、自引用、后代循环或同层名称冲突。虽然当前 TagsView 主要按语义来源分组而不是显示父子树，数据合同已经允许层级，后续扩展本体或别名时会继承损坏数据。

**落实方案：** 与文件夹共用通用的无环树校验模式，但保持两个领域服务分离；当前 UI 未启用标签树前，禁止 renderer 任意修改 `parent_id`，只允许受控维护命令使用。

### D04-P2-02 扫描错误被折叠为空数组，用户无法区分“没有文件”和“扫描失败”

**证据等级：已确认。**

外部文件夹不存在、递归中任一异常和真实空目录最终都可能返回 `[]`（`src/main/ipc/folders.ts:756` 至 `src/main/ipc/folders.ts:779`）。renderer 无法给出恢复动作，日志中的绝对路径也可能泄露不必要信息。

**落实方案：** 返回统一 envelope：`status`、`jobId`、`discoveredCount`、`errorCount`、脱敏错误码和可重试动作；详细绝对路径只在用户主动打开本地诊断时显示。

### D04-P2-03 文库状态缓存“脏快照”缺少可见版本和一致性承诺

**证据等级：已确认。**

缓存标脏后读取会返回旧快照并后台调度刷新，这对响应速度合理，但 UI 主要依赖 `dirty` 决定是否应用文件夹计数，没有向用户或调用方表达数据版本、刷新失败和最后成功校准差异。刷新异常被空 catch 吞掉（`src/main/library-state-cache.ts:91` 至 `src/main/library-state-cache.ts:103`）。

**落实方案：** 保留最终一致缓存，但返回 `snapshotVersion/sourceVersion/refreshStatus/lastErrorCode`；刷新失败可重试并进入健康中心，旧计数显示为“正在更新”而不是悄悄长期停留。

## 5. 目标架构

```text
Renderer organization views
  -> paged query APIs
     -> Library Query Service
        -> folder metadata/count projection
        -> visible-folder preview query
        -> paged tags/documents

Renderer explicit commands
  -> Organization Command Service
     -> validate invariants
     -> preview rename/merge/move impact
     -> transactional idempotent write
     -> emit library projection version

Background Job Coordinator
  -> external folder scan
  -> metadata tag rebuild
  -> AI reclassification
  -> count calibration
     each: bounded batch + cursor + heartbeat + cancel + resume
```

核心原则：

- GET/列表接口必须纯读取，不能隐式合并、清理或保存。
- 移动、改名、合并和批量关联是不同命令，破坏性行为必须显式预览和确认。
- 数据总量可以增长，单次 IPC、SQL 参数、worker 批次、renderer 列表和内存对象必须有界。
- 计数允许短暂最终一致，但必须有版本、刷新状态和可校准机制。
- 现有 SQLite 表和用户关系原位兼容；新增结构是可选优化，不是正确性的前提。

## 6. 分阶段落实方案

### 阶段 A：组织关系完整性护栏

- 收口文件夹和标签父级校验，所有 IPC 复用后端不变量。
- 把同名文件夹自动合并改为冲突响应和显式合并命令。
- 把 `tags:list` 改为纯查询，移除读取时自动合并和删除。
- renderer 树工具加入循环保护，并提供旧库诊断预演。
- 先补运行时 SQLite 测试，再改实现；不迁移数据库。

### 阶段 B：有界查询与侧栏投影

- 总览拆成文件夹元数据/计数和可见预览两类 API。
- 用数据库聚合替代 JS 全库文献 ID 集合。
- 标签页、文件夹旧 API 和所有选择器加入游标分页。
- 统一 chunk helper，消除无界 `IN (...)`。
- 给状态缓存增加版本、刷新状态、失败报告和任务去重。

### 阶段 C：持久化组织任务

- 外部目录扫描、元数据标签重建、AI 重分类复用模块 02/03 的同一后台任务框架，不另建调度器。
- 每个任务保存真实游标、heartbeat、取消位、失败项和输入版本。
- 重启后从已提交批次继续，不重复已完成副作用。
- 任务并发使用设置页的用户配置；默认值保守，任务数量不设上限。

### 阶段 D：大库交互与批量语义

- 标签和文献选择器采用分页/虚拟列表，保持跨页选择。
- 明确当前页、已加载和当前筛选全集三种选择范围。
- 大批量关系变更显示预计数量、阶段、成功/跳过/失败和撤销入口。
- 文件夹卡片按可见区域懒加载预览，返回文库时恢复滚动和筛选状态。

### 阶段 E：组织智能化

- 引入可解释的建议收件箱：重复标签、未分类文献、可疑文件夹和待确认 AI 分类均先建议、后应用。
- 古籍/地方志与通用论文通过不同元数据预设、标签词表和规则模板兼容，不拆成两套文库。
- 自动化规则只能操作用户明确选择的范围，并保留执行日志和撤销。

## 8. 新功能建议

### 8.1 智能整理收件箱

**用户问题：** 新导入文献、OCR 补全元数据和 AI 分类会持续产生待整理项，用户现在需要分别进入文库、标签和文件夹页面查找。

**MVP：** 一个统一收件箱，分页展示“未分类、疑似重复标签、可疑标题、缺失元数据、AI 建议分类、外部目录新增文件”。每条建议显示证据和影响，支持接受、修改、忽略、批量处理。

**实现影响：** 复用现有智能视图、健康报告和后台 job；第一版把忽略记录和规则保存在 settings JSON，不迁移业务表。所有动作调用显式组织命令，不直接写数据库。

**验收与回退：** 关闭功能后不改变现有文库；忽略/接受可撤销；任何建议生成失败只影响该卡片，不阻塞导入和阅读。无需新依赖。

### 8.2 智能集合与保存的筛选器

**用户问题：** 研究者经常重复组合“朝代、作者、标签、OCR 状态、阅读状态、年份和全文命中”等条件，普通文件夹无法自动更新。

**MVP：** 将当前文库筛选保存为只读智能集合，支持名称、图标、排序和固定到侧栏。集合保存查询 AST，不复制文献关系；古籍预设与论文预设共享同一查询引擎。

**实现影响：** 第一版可存 settings JSON；当集合数量、共享或版本历史需要结构化查询时，再评估新增 `saved_views` 表。查询 AST 必须版本化并允许旧版本兼容读取。

**验收与回退：** 文献字段变化后集合结果自动更新；删除集合不删除文献；旧客户端忽略未知 settings 键。无需新依赖。

### 8.3 标签别名、本体与受控合并

**用户问题：** 古籍存在繁简、异体字、朝代别称和责任者异名；论文又有缩写、主题词和机构别名。直接宽松合并会丢失语义，完全不归一化又降低检索召回。

**MVP：** 标签保留唯一实体，另建别名映射；搜索命中别名时返回主标签，界面仍显示用户选择的原词。合并必须预览并保留旧 ID 到新 ID 的重定向记录。

**实现影响：** MVP 可先将 alias 放在标签 metadata/settings 映射；若需要高性能全库检索，再申请兼容新增 alias 表。不得自动调用外部词典。

**验收与回退：** 繁简词可以关联但不被强制合并；删除别名不删除主标签或文献关系；导出可选择原词或规范词。无新依赖。

### 8.4 外部资料库增量同步

**用户问题：** 用户会持续把 PDF、图片和文本放入电脑目录，当前每次需要重新扫描并手工判断新增、改名和删除。

**MVP：** 保存目录指纹，用户主动点击同步时只展示新增、变化、缺失和冲突；确认后把新增项送入持久化导入队列。默认不自动删除文库文献，也不后台常驻监视。

**实现影响：** 复用现有文件 fingerprint、导入队列和扫描 job。第一版使用 Node 标准库主动扫描，不新增 watcher 依赖；若后续需要跨平台实时监视，任何新 watcher 依赖都标记 **实施前需用户确认**。

**验收与回退：** 路径离线时只显示“暂不可用”；重新连接后继续比较；关闭同步不影响已导入文献，目录外文件绝不访问。

### 8.5 可撤销的批量整理规则

**用户问题：** 大型文库需要把重复动作自动化，但直接自动移动或改标签风险高。

**MVP：** 用户用现有筛选器定义“当条件满足时建议加入文件夹/添加标签/标记待校对”，先预演命中数量和样例，再生成可撤销批次。默认只建议，不自动执行。

**实现影响：** 规则使用版本化 AST，执行进入组织 job；操作日志记录原关系和新关系。第一版不支持脚本或任意代码，避免安全边界扩大。

**验收与回退：** 同一规则重复执行幂等；撤销只恢复本批次改动且不覆盖之后的人工修改；关闭规则不删除结果。无需新依赖。

## 9. 依赖、迁移与审批

- 阶段 A、B 可以使用现有 better-sqlite3、Electron、React、Zustand、Node 标准库和 worker_threads 完成，不新增依赖。
- 第一阶段保留现有数据库表，不修改或删除用户字段；旧库循环检测、标签合并和文件夹合并都先预演，不自动迁移。
- 组织任务复用模块 02/03 已审批的统一 job/item 表，不再申请同义表。若后续新增 alias、saved view、增量计数或操作日志表，必须采用旁路新增、自动备份、事务、失败回滚、旧版本忽略新表和恢复演练；只有实测证明 settings JSON 或现有统一任务表无法满足可靠性或性能时才执行。
- 实时文件监视库、同步服务、云端词典、知识图谱库或新的本地模型均属于候选，必须单独评估许可证、包体、Windows 行为、隐私和回退，并标记 **实施前需用户确认**。

## 10. 与其他模块的约束

- 导入模块只能向持久化组织 job 投递文件和初始目标文件夹，不能把扫描结果一次性塞入 renderer。
- OCR 与元数据模块产生的标签必须带来源、置信度、输入哈希和版本；人工关系优先，自动任务不得覆盖。
- 检索模块的文件夹/标签筛选必须使用同一范围解析和 selection token，不能各自复制 1000 条静默上限。
- AI 模块不得在启动时仅凭存在 API Key 自动上传全文；分类建议先进入可复核收件箱。
- 数据库模块提供写维护互斥、任务快照和恢复边界；组织任务不得与恢复、备份或孤立文件清理互相踩踏。
- UI 与交互模块负责明确选择范围、冲突预览、进度、撤销、键盘和可访问性，但所有完整性校验仍必须在 main 进程执行。
- 新版验收先于正式实现更新；组织完整性、读接口纯度和超大库有界性属于发布阻断门槛。
