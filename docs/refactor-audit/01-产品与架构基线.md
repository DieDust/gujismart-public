# 01 产品与架构基线

## 1. 本章结论

GujiSmart 已经具备较完整的本地优先研究工作台能力，Electron main、preload、renderer、SQLite 与公开回归脚本之间也已经形成明确边界。当前最主要的问题不是缺少功能，而是功能持续增长后，跨领域职责集中到少数超大文件，状态和数据结构开始出现多套语义，导致后续任何一次优化都容易同时影响导入、OCR、阅读器、检索、AI、设置和数据库。

本轮重构不应从“大规模重写”开始。建议先建立稳定的领域合同、设置注册表、任务状态机和兼容适配层，再按功能闭环逐步拆分。第一阶段可以不迁移现有数据库、不更换框架、不新增依赖，并保持现有 IPC 名称和用户数据可读。

## 3. 当前运行架构

```text
React renderer
  -> window.api（preload，显式类型）
  -> ipcMain.handle（按领域注册）
  -> main 服务 / SQLite / 文件系统 / OCR 与 AI 外部服务
  -> typed response / progress event
  -> renderer store、view 和工作区状态
```

### 3.1 已经做对的基础

- `contextIsolation: true`、`nodeIntegration: false`，renderer 不直接使用 Node 或 Electron。
- 外部链接经过 `http/https` 校验，本地文件协议经过数据目录、PDF 仓库和运行时授权路径白名单校验。
- IPC 使用 `domain:action` 命名，并有 AST 级检查验证 preload、main 和 renderer 是否互相缺失。
- TypeScript 开启 `strict`，共享纯函数逐步从 main 中抽出，并有模块分层回归保护。
- SQLite 使用 WAL，搜索索引 worker 与健康报告 worker 已从主线程分离部分重任务。
- 公开检查不依赖真实语料、真实数据库或 API Key，开源卫生和乱码检查已进入默认门禁。
- 数据库已经包含兼容迁移、备份、安全备份、外置大字段和旧搜索索引治理基础。

这些能力应当保留并作为重构护栏，不应因为拆分文件而改变用户可见行为。

## 4. 关键问题

### A01-P1-01 Dashboard 的“全部文献”统计最多只覆盖默认 1000 条

**证据等级：已确认。**

`DashboardView` 调用 `listDocuments({})` 后在 renderer 中用数组长度和过滤统计状态（`src/renderer/src/views/DashboardView.tsx:38`）。`documents:list` 的查询默认附加 `LIMIT 1000`（`src/main/ipc/documents.ts:2979`、`src/main/ipc/documents.ts:2981`）。因此超过 1000 篇时，“全部文献”和各状态数量会被截断，并且会把最多 1000 条完整列表跨 IPC 传给 renderer。

**优化方案：**

1. 新增只返回聚合值的 `library:getProcessingSummary` 或扩展现有 library state cache。
2. SQL 直接计算总数和各 `import_status` 数量，不加载文献行。
3. 保留 `listDocuments` 兼容接口，不让旧调用方失效。
4. 新版验收至少构造 1001 条、10 万条两档数据，验证统计准确且响应内存不随总量线性增加。

### A01-P1-02 OCR、导入和通用状态信封的终态语义不一致

**证据等级：已确认。**

- `OcrStatus` 没有 `canceled`，但 `OcrProgressPhase` 和进度事件支持 `canceled`（`src/shared/types.ts:8`、`src/shared/types.ts:672`、`src/shared/types.ts:685`）。
- OCR error 会给出 `review_ocr_settings_or_retry`，同时被标记为 `recoverable: false`（`src/shared/status-envelope.ts:49` 至 `src/shared/status-envelope.ts:60`）。动作提示和恢复语义冲突。
- `ImportProgressEvent` 只有 `copying`、`hashing`、`stored`，没有 error 或 canceled 终态（`src/shared/types.ts:403` 至 `src/shared/types.ts:414`）；转换函数又把所有导入事件固定标为可恢复（`src/shared/status-envelope.ts:63` 至 `src/shared/status-envelope.ts:70`）。

**优化方案：**

建立共享、闭合的顶层任务状态词表：

```ts
type TaskStatus = 'queued' | 'running' | 'paused' | 'completed' | 'error' | 'canceled'

interface TaskStateEnvelope {
  status: TaskStatus
  phase: string
  blockedReason?: string       // 只与 paused 搭配
  commandState?: 'pausing' | 'canceling'
  completionKind?: 'complete' | 'partial' // 只与 completed 搭配
  error?: { code: string; recoverable: boolean; retryPolicy?: string } // 只与 error 搭配
  updatedAt: string
}
```

每个领域可以保留自己的 phase，但顶层 status、终态、错误码、恢复能力、重试建议和更新时间必须一致。`failed` 兼容映射为 `error`，`cancelled` 映射为 `canceled`，`partial` 只能成为 `completed + completionKind='partial'`，credential/budget/review 等阻塞使用 `paused + blockedReason`。非法组合由 main 运行时拒绝；显式 retry 创建新 attempt 并把 task 迁回 queued。实施时先新增兼容字段并双写，renderer 完成迁移后再停止读取旧字段；现有数据库状态列先不迁移，通过适配器映射。

### A01-P1-03 设置保存不是一个原子操作，也没有统一设置 schema

**证据等级：已确认。**

共享合同将设置表示为 `Record<string, string>`（`src/shared/types.ts:1686` 至 `src/shared/types.ts:1691`），main 的 `settings:set` 接受任意 key/value 并立即保存（`src/main/ipc/settings.ts:608` 至 `src/main/ipc/settings.ts:630`）。设置界面保存时遍历全部表单字段，逐个等待 IPC，再单独保存自动化、批处理、备份、快捷键和服务商配置（`src/renderer/src/views/SettingsView.tsx:790` 至 `src/renderer/src/views/SettingsView.tsx:844`）。中途失败会留下部分新值、部分旧值，且 renderer、main 与各业务模块各自解析字符串默认值。

**优化方案：**

1. 建立 `SettingDefinition` 注册表，至少包含 key、类型、默认值、解析器、校验器、是否敏感、适用模式和兼容别名。
2. 新增 `settings:validatePatch` 和 `settings:applyPatch`，一次提交一个 typed patch，并在 SQLite 事务中写入。
3. 保留 `settings:get`、`settings:set`、`settings:getAll` 只兼容非敏感 key；所有 protected key 的 generic 读取/写入必须拒绝或脱敏，新代码只使用 typed settings service。
4. typed settings service 与模块 03/07 共用唯一 `CredentialVault`，由本模块拥有 entry/version/journal 与 public profile 合同。已保存 API Key 不返回 renderer、不进入普通备份、诊断、错误或日志；UI 只显示 configured/last4/version。
5. 新版验收覆盖字段校验、批量提交失败回滚、旧设置读取、默认值升级、三类凭据迁移、vault/SQLite 跨存储故障和敏感值脱敏。

**跨模块优先级修正：** D03-P0-01 与 D07-P0-01 已确认 LLM、视觉 OCR、PaddleOCR 凭据处于明文泄露状态。CredentialVault 是独立 P0 前置切片，优先于下述阶段 A 至 F；A01-P1-03 的一般设置重构不能把凭据整改延后，也不能另建第二套 secret 存储。

### A01-P1-04 SQLite busy 重试可能阻塞 Electron 主进程

**证据等级：高风险推断，需基准验证。**

主数据库用 `Atomics.wait` 实现同步 sleep（`src/main/database.ts:32` 至 `src/main/database.ts:35`），显式保存的 busy 重试延迟合计 2775 ms（`src/main/database.ts:29` 至 `src/main/database.ts:54`），且每次 SQLite 调用还可能等待 250 ms。现有回归只断言常量和代码片段存在（`scripts/database-busy-retry-regression.js:12` 至 `scripts/database-busy-retry-regression.js:33`），没有测量 UI 心跳、IPC 延迟或真实锁竞争。

**优化方案：**

- 先增加锁竞争基准：worker 持有写锁，主进程同时执行保存，记录 renderer heartbeat、IPC p95/p99 和最长冻结时间。
- 普通后台 checkpoint 遇 busy 立即让出并重排；关机、手动备份等必须完成的操作显示状态并在 worker 或独立维护阶段处理。
- 不在没有测量数据时直接更换数据库或引入异步 ORM。

### A01-P2-01 多个中央文件已经成为跨领域巨型模块

**证据等级：已确认。**

| 文件 | 行数 | 当前混合职责 |
| --- | ---: | --- |
| `src/shared/types.ts` | 2864 | 几乎全部领域 DTO、数据库行、事件和设置类型 |
| `src/preload/index.ts` | 803 | 273 个 API 的单一对象与事件订阅 |
| `src/main/database.ts` | 2466 | 数据目录、Schema、迁移、种子、维护、FTS 和公共查询 |
| `src/main/ipc/settings.ts` | 1130 | 设置、应用更新、导出、排版、文件读取、远程图片和备份 |
| `src/renderer/src/App.tsx` | 2829 | 导航、标签组、拖拽、工作区恢复、数据库升级、AI 浮窗和全局快捷键 |
| `src/renderer/src/views/SettingsView.tsx` | 3099 | 全部设置领域、服务商管理、备份、数据库维护和术语表 |

`registerAllIpcHandlers` 也从 `settings.ts` 同时导入六个不同领域的注册函数（`src/main/ipc/index.ts:10`、`src/main/ipc/index.ts:29` 至 `src/main/ipc/index.ts:35`）。

**优化方案：**

按领域渐进拆分，保留兼容 barrel：

```text
src/shared/contracts/{documents,import,ocr,reader,search,ai,settings,...}.ts
src/shared/types.ts                         # 临时兼容重导出
src/main/domains/<domain>/{repository,service,ipc}.ts
src/preload/domains/<domain>.ts
src/preload/index.ts                       # 只组合 API
src/renderer/src/features/<domain>/...
```

拆分顺序应以“降低一起变化的文件数量”为目标，不以追求小文件数量为目标。每次只迁移一个领域并保持 IPC 名称、响应结构和数据库读取兼容。

### A01-P2-02 SQLite snake_case 行结构大量泄漏到 renderer

**证据等级：已确认。**

架构规范要求 renderer-facing DTO 使用 camelCase，并在边界转换（`docs/ARCHITECTURE.md:16` 至 `docs/ARCHITECTURE.md:24`）。但 `Document`、`DocumentListItem`、`Page`、翻译缓存、研究记录等共享类型直接暴露 `doc_id`、`page_num`、`ocr_status`、`created_at` 等数据库字段，例如 `src/shared/types.ts:865` 至 `src/shared/types.ts:889`、`src/shared/types.ts:984` 至 `src/shared/types.ts:1003`、`src/shared/types.ts:1221` 至 `src/shared/types.ts:1234`。

**优化方案：**

- 保留现有 row type，重命名为 `DocumentRow`、`PageRow` 等，仅供 main/repository 和兼容接口使用。
- 新增 camelCase DTO 与集中 mapper；新 IPC 只返回 DTO。
- 旧接口继续返回旧形状，直至调用方逐步迁移。禁止一次性改全库字段或强制数据库迁移。

### A01-P2-03 IPC 检查偏重“名称存在”，缺少运行时合同与取消语义

**证据等级：已确认。**

现有 `check-ipc-contract` 能检查缺失、重复和 renderer optional probe；`function-contract-regression` 通过 API 名称清单和最低数量保护功能面。这能防止接口被意外删除，但不能证明：

- 参数结构在 renderer、preload、main 间一致。
- 返回值满足 shared 类型。
- 事件订阅能正确取消，重复挂载不会泄漏。
- 长任务有 request/job id、取消、超时、幂等和恢复合同。

**优化方案：**

建立逐领域合同测试，至少对关键 IPC 进行序列化 round-trip、错误信封、取消、重复请求和旧 payload 兼容测试。现有 AST 检查继续保留，不能用新测试替代它。

### A01-P2-04 Electron 安全基线需要专项威胁建模和渐进收紧

**证据等级：已确认配置，高风险需专项验证。**

- BrowserWindow 使用 `sandbox: false`（`src/main/index.ts:178` 至 `src/main/index.ts:193`）。
- `local-resource` 协议启用 `bypassCSP` 和 CORS（`src/main/index.ts:446` 至 `src/main/index.ts:455`）。
- renderer CSP 允许 inline style、Google Fonts 和若干外部 API 域（`src/renderer/index.html:6` 至 `src/renderer/index.html:10`）。
- 当前文件协议仍有路径白名单保护，外链也有协议校验，所以不能把配置直接描述成可利用漏洞。

**优化方案：**

1. 为本地文件、拖拽路径、远程图片、外链、API Key 和渲染 HTML 建立威胁模型与自动化负例。
2. 先验证 preload 在 sandbox 模式下的兼容性，再考虑开启；失败时保留回退开关。
3. 评估移除 `bypassCSP`、限制 CORS、将字体随应用打包，以及把外部连接统一收敛到 main。
4. 所有收紧均需 Windows 安装版、便携版、PDF.js、EPUB、原图阅读和 OCR 图片回显回归。

### A01-P2-05 生产错误页直接显示完整 stack

**证据等级：已确认。**

renderer 错误边界把 `error.stack` 展示在界面（`src/renderer/src/main.tsx:27` 至 `src/renderer/src/main.tsx:38`），可能暴露本地安装路径、内部模块名或用户路径。

**优化方案：**

默认只展示稳定错误编号和可执行恢复操作；“复制诊断”生成脱敏报告。开发模式可以保留 stack，生产模式不直接显示绝对路径。

### A01-P2-06 CI 与 Release 没有采用最省时的失败顺序

**证据等级：已确认。**

CI 先 build 后 check（`.github/workflows/ci.yml:27` 至 `.github/workflows/ci.yml:31`）；Release 先生成 Windows 安装包，再执行 check（`.github/workflows/release.yml:48` 至 `.github/workflows/release.yml:55`），且两个工作流都没有执行 Electron smoke。

**优化方案：**

推荐顺序：`npm ci -> check -> build -> smoke -> build:win -> artifact/release`。Release 可复用已通过的 CI commit，避免为已知失败提交生成安装包。工作流变更属于发布模块，正式实施前需验证 GitHub 权限、缓存、原生依赖和构建时长。

### A01-P2-07 “异体字规范化”混合了繁简转换与古籍异体字修改

**证据等级：已确认。**

`VARIANT_MAP` 同时包含繁体转简体和古籍异体字映射，并提供一键改写文本的 `normalizeVariants`（`src/renderer/src/utils/variants.ts:1` 至 `src/renderer/src/utils/variants.ts:135`）。对古籍原文，`發/发`、`餘/余`、`於/于` 等并不只是无损显示转换；直接保存会改变史料文本。

**优化方案：**

- 原始 OCR、校对原文和展示转换分层保存。
- 默认只检测并提示，不自动覆盖原文。
- 用户确认修改时记录原字、建议字、位置、操作者和时间，支持撤销。
- 搜索归一化可以使用单独索引字段，不反写原文。

## 5. 目标架构

### 5.1 保留三进程边界，按领域组织

不更换 Electron、React、TypeScript、Vite、Ant Design 或 SQLite。目标是让每个用户流程在 shared、preload、main 和 renderer 中有同名领域边界：

```text
import  -> queue -> OCR -> document state -> search index
reader  -> page window -> proof -> save -> reindex
search  -> candidate -> verified hit -> reader locator -> excerpt/AI evidence
AI      -> scope -> retrieval -> evidence -> answer/report -> trace snapshot
```

### 5.2 统一领域合同

每个合同至少包含：

- request/response DTO。
- 稳定错误码与恢复动作。
- job/progress 事件和取消语义。
- 兼容版本或 capability 字段。
- 数据来源、更新时间和必要的 trace id。

`src/shared/types.ts` 暂时继续重导出旧名称，避免一次性修改 273 个 preload API。

### 5.3 统一任务与容量模型

文献和任务数量逻辑上不设上限，但所有列表、队列和缓存必须满足：

- 数据库分页或游标读取。
- 持久化队列，重启后可恢复。
- 用户设置只控制并发，不控制可接收的总任务数。
- 每个 worker 有明确内存、缓存、重试和超时上限。
- UI 只订阅当前可见窗口和聚合统计，不持有全库数组。

### 5.4 数据库兼容优先

第一阶段不改表名、不改现有列、不删除旧字段。需要新结构时采用：

1. 预检数据库版本与空间。
2. 自动创建安全备份。
3. 增量新增表/列或旁路数据。
4. 新旧读取兼容一段版本周期。
5. 事务失败回滚和恢复演练。
6. 明确的降级路径和可重复迁移。

只有基准证明收益显著时，才批准会重写大量数据的迁移。

## 6. 分阶段落实方案

**P0 前置切片：** 先完成唯一 CredentialVault sidecar/journal、protected-key generic IPC 封闭、三类旧明文迁移、模型列表 draft ref 和普通/历史备份脱敏。该切片允许 additive settings/vault 引用迁移；其余阶段仍遵守数据库兼容优先。

### 阶段 A：合同与基准护栏

- 为导入、OCR、索引、阅读器和 AI 建立统一状态词表和字段矩阵。
- 记录现有 IPC payload 快照、数据库版本、构建体积、启动时间、空闲内存、1000/10 万文献列表和锁竞争基线。
- 为 Dashboard 统计截断、设置部分保存和任务 canceled 语义增加目标成品验收。
- 不改变用户数据和默认行为。

### 阶段 B：共享合同渐进拆分

- 新建按领域的 `src/shared/contracts/` 文件。
- `src/shared/types.ts` 只做兼容重导出并逐步减少直接定义。

## 8. 新功能方向

### 8.1 工作模式预设

提供“古籍/扫描史料”“现代论文/PDF”“自定义”三类预设，只改变默认阅读、OCR、校对、检索和 AI 策略，不把产品拆成两个版本。

- 古籍模式：原貌优先、异体字只提示、竖排/版式校对、繁简检索扩展。
- 论文模式：文本层优先、双栏识别、引用和 DOI/作者元数据优先。
- 用户可以逐项覆盖预设，已有用户默认沿用当前行为。

### 8.2 系统健康中心

把分散的数据库、OCR 服务商、AI 服务商、备份、索引和源文件状态汇总为只读健康页，展示可操作问题和恢复动作，不展示私密正文或密钥。它可以复用现有诊断协议，不需要新依赖。

### 8.3 可复现诊断包

用户主动导出脱敏诊断包，包含版本、平台、配置有效性、任务错误码、索引/数据库统计和最近一次失败 trace，不包含文献正文、真实路径和 API Key。用于开源 issue 和后续远程排障。

### 8.4 能力降级提示

在没有 OCR Token、没有 AI Key、原 PDF 缺失或索引维护中时，界面明确显示“哪些功能仍可用”，而不是把整个流程视为失败。能力矩阵由 main 返回，renderer 只负责呈现。

## 9. 依赖、风险与审批

- 本章基础重构不需要新增依赖。
- 可以使用现有 TypeScript、Zustand、Ant Design、better-sqlite3 和 Node 标准能力完成。
- 若后续拟引入 schema validator、日志/trace SDK、自动更新器、本地模型或新的数据库组件，必须单独列出许可证、安装体积、安全、维护成本、离线能力和回退方案，并在实施前征得用户确认。
- 安全收紧、数据库迁移和任务状态兼容是跨模块热点，必须在导入、OCR、阅读器、检索和 AI 章节完成后再确定最终实施顺序。

## 10. 与后续模块的约束

- 导入和 OCR 不得再各自发明一套任务终态。
- 阅读器、检索和 AI 必须使用同一文献/page locator 和证据来源标识。
- UI/交互优化不得绕过 preload 直接访问文件或外部服务。
- 性能优化不得通过一次性加载全库、无限并发或静默降低准确率实现。
- 所有数据库建议默认兼容现有库；需要迁移时必须附备份、回滚、双读和恢复演练。
- 原文、校对文本、显示转换和搜索归一化必须分层，避免古籍文本被不可逆改写。

## 11. 第二、第三步实施结果（2026-07-10）

- typed settings registry 已建立：三类 protected key、boolean/integer 公共设置和未知旧 key 兼容写入均有运行时校验；未知 key 不会因此获得 secret 读取能力。
- main-only CredentialVault 已使用 Electron `safeStorage` 与 `userData/secrets/credentials.v1.json` sidecar/journal 落地。旧 `llm_api_key`、`vision_ocr_api_key`、`paddleocr_api_key` 和 profile 内嵌 Key 先加密回读验证，再从 SQLite 明文行/JSON 删除。
- renderer 只收到 `configured/last4/version/state`；设置页、引导页和 profile 事件不回填已保存 secret。新草稿通过 owner/purpose/TTL/一次性 credential draft ref 提交，通用 `settings:set` 明确拒绝 protected key。
- `TaskStatus` 已闭合为 `queued|running|paused|completed|error|canceled`，新增 `TaskStateEnvelope`、`ErrorEnvelope`、`SettingDefinition` validator；现有 background event 同时携带规范化 `taskState`，旧字段继续兼容。
- 本切片没有建立 `task_jobs/task_items`。唯一 scheduler、lease/cursor/attempt/event/artifact 仍是迁移顺序第 4 步，不得因共享合同已存在而标记完成。
