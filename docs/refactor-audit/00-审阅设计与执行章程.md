# GujiSmart 全面重构审阅设计与执行章程

## 1. 目标

完整阅读 GujiSmart 当前仓库的代码、测试、配置、规范与发布流程，形成能够直接指导后续实现的分模块优化设计。设计同时服务古籍、地方志和扫描史料研究者，以及通用 PDF、论文和现代文献研究者；出现需求差异时优先通过模式、预设和可配置策略兼容，而不是拆成两个产品。

本阶段只允许修改审阅文档并删除用户明确废弃的旧优化建议目录，不修改任何业务代码、数据库结构、依赖或发布配置。

## 2. 事实来源与约束

- 当前活跃仓库 `gujismart` 是开发、开源和发布的唯一事实来源。
- 旧 `gujismart-public` 目录不作为代码基线，只在必要时用于历史兼容性核对。
- 必须遵守根目录 `AGENTS.md`、`docs/ARCHITECTURE.md`、`docs/SCRIPTS.md`、`docs/ROADMAP.md`、Trellis 思考指南和项目内发布流程。
- renderer-facing 能力变更必须同步考虑 `src/shared/types.ts`、`src/preload/index.ts`、`src/main/ipc/` 与 renderer 调用方。
- 不读取、记录或提交用户数据库、真实文献、API Key、日志、构建产物和临时调试输出。
- 中文文档使用 UTF-8，通过 `apply_patch` 修改，并在提交前执行乱码检查。

## 3. 覆盖范围

### 3.1 必须逐一审阅

- Git 已跟踪的 TypeScript、TSX、JavaScript、CSS、HTML、JSON、YAML、Markdown 和安装脚本。
- `src/main`、`src/preload`、`src/renderer`、`src/shared` 的全部产品代码。
- `scripts` 下的全部公开回归、检查、构建和维护脚本。
- 根目录元数据、GitHub Actions、打包配置、开源许可证与贡献规范。
- 项目本地但未纳入 Git 的维护规范与工作流，只作为约束，不复制到公开文档。

### 3.2 只做合规与用途检查

- PNG、ICO、PDF、DOCX、EXE、DLL 等二进制文件。
- `resources/vendor` 中的第三方运行时，检查来源、许可证、体积和打包边界，不做源码级逆向。

### 3.3 明确排除

- `node_modules`、`out`、`dist`、`data`、`output`、`tmp`、`.tmp-*`、本地 Electron profile 和用户数据目录。
- 私有语料、真实数据库、真实 OCR 返回、真实研究笔记和任何凭据。

## 4. 审阅顺序

```text
规范、架构、共享类型
  -> 导入与持久化队列
  -> OCR 与识别数据
  -> 数据库、索引和文库组织
  -> 阅读器与校对
  -> 全库与全文检索
  -> AI 对话与 AI 研究
  -> 翻译、引用、导出和研究写作
  -> UI 视觉与跨页面交互
  -> 性能、稳定性、安全、备份和开源发布
  -> 新功能路线图
  -> 全局冲突与兼容性复核
```

中央文件先建立整体认识，再在相关模块中复核。每个文件只有一个主归属，同时可以登记多个影响模块。

## 5. 单模块审阅闭环

1. 列出模块涉及的源码、共享类型、IPC、数据库、界面和回归脚本。
2. 逐文件完整阅读，登记职责、依赖、关键数据结构、状态与副作用。
3. 追踪完整数据流和失败路径，核对跨进程字段、错误语义、持久化和恢复行为。
4. 使用现有回归脚本、静态搜索或只读基准验证重要判断；没有证据时明确标记为待测风险。
5. 持续写入当前模块文档，不在全部审阅结束后依赖记忆补写。
6. 为每项建议记录优先级、用户收益、实现边界、兼容影响、新版验收、风险与回退。
7. 自检建议是否违反现有数据库、IPC、隐私、许可证、打包和发布约束。
8. 执行文档门禁并独立提交模块文档。

## 6. 证据与优先级

### 6.1 证据等级

- **已确认**：代码、配置或现有测试可以直接证明。
- **已测量**：有可重复的基准或运行结果。
- **高风险推断**：代码结构显示明确风险，但需要新增测试或基准确认。
- **产品建议**：未来能力，不描述为现有缺陷。

### 6.2 优先级

- **P0**：数据丢失、隐私安全、崩溃、不可恢复损坏。
- **P1**：核心流程错误、明显卡顿、结果不稳定、任务无法恢复。
- **P2**：易用性、一般性能和可维护性问题。
- **P3**：增强功能与长期演进。

没有实测数据时不得写伪精确收益。所有性能建议都要附测量方式，先记录当前基线，再定义目标成品指标。

## 7. 目标成品与新版验收

现有测试只用于识别当前行为和回归边界。正式实施每个优化切片前，先根据目标成品更新验收方案：

```text
需求编号 -> 目标行为 -> 验收场景 -> 自动化测试
         -> 性能/稳定性指标 -> 兼容要求 -> 实施任务 -> 验证结果
```

旧测试逐项归类为继续保留、因产品行为改变而更新、或由新测试替代。任何修改或删除都必须说明原因。成品验收以新版方案为主，同时执行数据兼容、IPC 合同、开源卫生、完整检查、构建、冒烟和 Windows 发布门禁。

## 8. 容量、迁移与依赖策略

- 文库和任务数量不设产品上限，所有大集合必须分页、流式、增量或持久化排队。
- 并发、缓存和内存由设置或明确上限控制，不随文库总量线性增长。
- 超大规模允许耗时增长，但不得丢任务、阻塞主要阅读流程或要求一次性载入全部数据。
- 默认兼容现有 SQLite 数据库、设置、OCR 结果和用户文件，优先零迁移。
- 只有迁移能带来显著收益时才列入候选，并必须包含预检、自动备份、事务、失败回滚、兼容读取和恢复演练。
- 可以建议成熟依赖、本地模型或新服务，但每项都必须单独列出许可证、体积、安全、维护和回退影响，并标记“实施前需用户确认”。

## 9. 新功能建议格式

每项新功能必须包含：

- 用户问题、目标用户和使用场景。
- 最小可用版本与完整操作流程。
- 对现有模块、IPC、数据库、设置和文件格式的影响。
- 隐私、许可证、外部服务、新增依赖和离线能力。
- 新版验收、失败模式、回退和兼容方式。
- 实施成本、风险、优先级和前置任务。

## 10. Git 与发布纪律

- 每个模块文档完成后独立提交，提交前检查 `git status`、相关差异、UTF-8、开源卫生和空白错误。
- 不提交 `dist`、`out`、`data`、安装包、日志、本地 profile 或临时文件。
- 全部设计完成后单独提交总路线图和冲突复核。
- 正式修改业务代码前，检查工作树、提交全部批准文档，并创建 `checkpoint/before-refactor-execution-<date>` 检查点提交与标签。
- 后续实现拆成可独立验证、发布和回滚的小计划；每个切片按新版验收先改测试，再实现，再执行窄测试与完整门禁。

## 11. 最终一致性复核

全部模块完成后重新完整阅读所有优化文档，建立跨模块矩阵，至少核对：

- 同一字段、状态、IPC、设置和数据库表是否出现不同定义。
- 导入、OCR、索引、阅读器、检索和 AI 对同一文献状态的理解是否一致。
- 性能优化是否牺牲准确性、可恢复性、隐私或可访问性。
- 新功能是否重复现有能力、引入隐式同步承诺或破坏本地优先原则。
- 实施顺序是否满足依赖，是否存在多个计划同时修改同一热点文件的冲突。
- 新版验收是否覆盖每项目标成品要求，并能在 CI、Windows 打包和本地回归环境中执行。
