# 02 导入与数据入库

## 1. 本章结论

GujiSmart 的导入链路已经具备较好的工程基础：PDF 复制与 SHA-256 可以在同一次流式读取中完成，导入和页记录写入会分块让出事件循环，队列快照已经从 renderer `localStorage` 迁入 SQLite，启动恢复能够修复一部分中断文档、压缩临时文件和孤儿目录。现有专项回归也全部通过。

但当前实现还不能满足“文献数量理论上不设上限，只按用户设置的数量持续分批处理”的目标。目录枚举、IPC payload、renderer 队列、SQLite 单行 JSON 快照、批次数组和导入后的自动 OCR 清单仍会一次性持有全部路径；每完成一批还会重新序列化整个剩余队列。导入文件、数据库行、文件夹关系、页图和后续 OCR 之间也没有统一的持久化任务边界，异常时主要依赖下次启动补偿，而不是在当前任务中完成幂等恢复。

本轮不建议重写 Electron、React、SQLite 或现有文献表。目标方案是保留 `documents`、`pages`、现有 IPC 和用户文件读取兼容，通过增量任务表、流式发现、有限预取、分阶段提交、内容指纹和可恢复的 OCR 交接逐步替换 renderer 内存队列。为保证超大任务量和页唯一性，建议批准两项收益明确的增量数据库迁移：持久化 job/item 表，以及清理历史重复页后建立 `(doc_id, page_num)` 条件唯一索引。两项迁移都必须先备份、可重入、可回滚，不改现有主表字段含义。

## 3. 当前导入闭环

```text
文件选择或拖入
  -> main 递归展开目录并返回全部路径
  -> renderer 去重并把全部路径放入内存队列
  -> 整个剩余队列序列化到 SQLite 单行 state_json
  -> renderer 按 batch_size 调 documents:import
  -> main 逐文件复制、解析并写 documents/pages
  -> renderer 写文件夹关系，启动预览队列
  -> renderer 在内存中启动后续自动 OCR
  -> 启动恢复处理部分 processing 文档、batch_queue 和孤儿文件
```

### 3.1 应保留的基础

- PDF 新文件使用 8 MB 缓冲区流式复制并可同时计算指纹，进度有节流，不会为了复制单个 PDF 先把整个文件读入内存（`src/main/pdf-assets.ts:427` 至 `src/main/pdf-assets.ts:514`）。
- PDF 会先以文件大小筛选可能重复项，只有必要时才提前计算 SHA-256；没有旧 size 元数据时，复制后仍会做 hash 查重（`src/main/ipc/documents.ts:3839` 至 `src/main/ipc/documents.ts:3902`、`src/main/ipc/documents.ts:4053` 至 `src/main/ipc/documents.ts:4108`）。
- JSON、EPUB 和 PDF 页记录已经按固定块写 SQLite，并在块之间让出事件循环（`src/main/ipc/documents.ts:3936` 至 `src/main/ipc/documents.ts:3963`、`src/main/ipc/documents.ts:2362` 至 `src/main/ipc/documents.ts:2403`、`src/main/ipc/documents.ts:684` 至 `src/main/ipc/documents.ts:715`）。
- 超过 1000 页的 PDF 在首次导入时延后创建空 page 行，OCR 或阅读时再补齐，避免导入热路径立即插入大量空记录（`src/main/ipc/documents.ts:671` 至 `src/main/ipc/documents.ts:745`、`src/main/ipc/documents.ts:4122` 至 `src/main/ipc/documents.ts:4207`）。
- 启动恢复能够识别中断的 processing 文档，修复图片页、补 PDF 页数，或把无法安全恢复的半成品转入删除任务（`src/main/startup-recovery.ts:383` 至 `src/main/startup-recovery.ts:548`）。
- 压缩不会阻塞普通 PDF 导入或 OCR 上传；qpdf 失败时保留原文件。中断压缩留下的 `.original-*` 文件也有启动恢复（`src/main/pdf-compression.ts:460` 至 `src/main/pdf-compression.ts:520`、`src/main/startup-recovery.ts:586` 至 `src/main/startup-recovery.ts:616`）。
- 导入正文完成后会把搜索索引标为 stale，由后台索引器处理，不在导入循环中同步重建全文索引（`src/main/ipc/documents.ts:4234` 至 `src/main/ipc/documents.ts:4240`）。

这些能力应保留并迁移到新的持久化调度器中，不能因为重构而退回一次性大数组、同步文件扫描或每页保存一次数据库。

## 4. 关键问题

### IMP-P1-01 当前队列并非真正的无限任务、有界资源模型

**证据等级：已确认。**

- main 递归扫描时把所有可导入路径放进 `files` 数组，目录队列还使用 `shift()` 消费（`src/main/ipc/documents.ts:777` 至 `src/main/ipc/documents.ts:808`）。
- `documents:resolveImportSources` 为每个目录返回完整 `filePaths`，再把全部路径一次性加入文件访问白名单（`src/main/ipc/documents.ts:3748` 至 `src/main/ipc/documents.ts:3791`）。
- renderer 再把所有目录结果展开到 `importFiles`、`Set`、`folderAssignments` 和 `ImportQueueJob.filePaths`（`src/renderer/src/views/LibraryView.tsx:4578` 至 `src/renderer/src/views/LibraryView.tsx:4613`）。
- 队列以一个 `LibraryImportQueueState.jobs[].filePaths[]` 结构存进单行 `state_json`（`src/shared/types.ts:236` 至 `src/shared/types.ts:247`、`src/main/database.ts:906` 至 `src/main/database.ts:912`）。每完成一批，renderer 对剩余数组做 `slice`，再把整个快照重新 `JSON.stringify` 和写库（`src/renderer/src/views/LibraryView.tsx:4040` 至 `src/renderer/src/views/LibraryView.tsx:4075`、`src/renderer/src/views/LibraryView.tsx:4279` 至 `src/renderer/src/views/LibraryView.tsx:4281`）。
- `processImportJob` 复制全部路径并一次性生成全部批次数组，还会累积整个任务的 `autoOcrQueue`（`src/renderer/src/views/LibraryView.tsx:4145` 至 `src/renderer/src/views/LibraryView.tsx:4165`）。

因此当前“分批”只限制一次 IPC 处理量，没有限制总路径数组、快照大小和重复序列化成本。对 N 个文件、批大小 B，剩余队列快照的累计序列化量接近 O(N²/B)。文件数足够大时，renderer、IPC 和 SQLite 字符串都可能先于真正导入成为瓶颈。

**优化方案：**

1. 把目录发现改为 main 侧 producer。枚举到一小批路径后直接写持久化 item，不再把完整目录清单返回 renderer。
2. 调度器只 claim 用户设置数量的待处理项，内存预取窗口固定为并发数的 2 至 4 倍；总任务数只存在 SQLite。
3. renderer 只接收任务聚合、当前项和分页错误列表，不持有全量路径。
4. `batch_size` 只定义并发或 claim 数量，不定义可接收总量。导入复制并发、OCR 并发和预览并发应拆成独立 typed 设置。
5. 旧 `library_import_queue_state` 只作为一次性迁移源，不再持续重写。

### IMP-P1-02 单项导入没有完整的分阶段提交和当前会话补偿

**证据等级：已确认。**

- JSON 先插入 `documents`，再按 50 页分事务写 `pages`，最后才标记 `processed`（`src/main/ipc/documents.ts:3927` 至 `src/main/ipc/documents.ts:3971`）。
- TXT/EPUB 先创建目录、复制文件，再解析源路径、插文献、写章节和目录，最后更新终态（`src/main/ipc/documents.ts:3979` 至 `src/main/ipc/documents.ts:4049`）。
- PDF/图片先复制到最终托管路径，之后才写文献和页记录（`src/main/ipc/documents.ts:4053` 至 `src/main/ipc/documents.ts:4219`）。
- 统一 catch 只返回失败结果，没有立即删除 staging、孤儿目录、processing 文献或部分 page 行（`src/main/ipc/documents.ts:4220` 至 `src/main/ipc/documents.ts:4231`）。

现有启动恢复可以在下次启动时修复或清理部分半成品，这是重要兜底，但当前会话仍可能留下 processing 文献、孤儿文件和已从队列移除的失败项。恢复逻辑不能替代正常任务的提交协议。

**优化方案：**

采用可恢复 saga，而不是试图把文件系统和 SQLite 伪装成一个事务：

```text
discovered -> staged -> validated -> committing -> stored -> downstream_queued -> completed
                    -> error(retryable/non-retryable)
                    -> canceled
```

1. 每个 item 先获得稳定 `itemId`、`documentId` 和 staging 目录。
2. 所有复制、hash、格式校验和解析从 staging 副本完成；不要复制后继续读取可能变化的外部源路径。
3. `documents` 和部分 page 行在 `committing` 阶段可以分块写，但普通文库查询不得把未提交文献当成可用成品。
4. 最后一个短事务同时更新文献终态、item 终态和下游 outbox/任务记录。
5. 普通异常在当前会话立即执行幂等补偿；进程崩溃时，启动恢复按 item phase 接续或清理。
6. 失败项必须留在任务表中，允许重试、跳过、导出错误清单或定位源文件，不能只显示第一条 toast 后丢失。

staging、孤儿清理、备份和恢复还必须复用模块 11 定义的全局存储维护锁。启动恢复不能在导入 item 仍持有有效 lease 时把其 staging 或托管目录判成孤儿。

### IMP-P1-03 页面重建先删除旧页，失败会破坏现有 OCR 与校对成果

**证据等级：已确认。**

`documents:savePages` 先清搜索索引并删除该文献全部 page 行，之后才每 8 页写 `page_N.jpg` 和插入新行（`src/main/ipc/documents.ts:4964` 至 `src/main/ipc/documents.ts:5015`）。`documents:appendPages` 的 reset 路径同样先删页，再写文件和分块提交（`src/main/ipc/documents.ts:5018` 至 `src/main/ipc/documents.ts:5081`）。磁盘满、无效图片、进程退出或任意一块写入失败时，旧 `ocr_text`、`proofed_text`、OCR 版本关系和搜索命中可能已经不可恢复。

非 reset 的同页更新也会直接覆盖稳定文件名，同时保留已有 OCR/校对文本；如果新图内容已经变化，文本和坐标会与图片失配（`src/main/ipc/documents.ts:5036` 至 `src/main/ipc/documents.ts:5064`）。

**优化方案：**

1. 新页先写 generation 专属临时目录和 staging rows，逐张校验图片、页号和总数。
2. 所有 staging 完成后，在一个数据库事务中切换活动 page set；事务失败时旧页保持不变。
3. 新 generation 激活后再异步清理旧文件和旧行；清理失败只产生健康告警，不影响阅读。
4. 替换了页面图像时，相关 OCR、坐标、校对和搜索状态必须显式标为 stale，除非内容指纹证明图像相同。
5. 在不增加 page generation 主表前，可以先用独立 staging 表实现事务 swap；是否增加 generation 外键由真实大文献基准决定。

### IMP-P1-04 导入队列在后续自动 OCR 真正持久化前就已经完成

**证据等级：已确认。**

每批文件返回导入结果后，renderer 立即从 `job.filePaths` 删除对应路径并保存队列快照（`src/renderer/src/views/LibraryView.tsx:4249` 至 `src/renderer/src/views/LibraryView.tsx:4281`）。全部文件入库后，自动 OCR 以 fire-and-forget Promise 启动（`src/renderer/src/views/LibraryView.tsx:4323` 至 `src/renderer/src/views/LibraryView.tsx:4337`）；`processImportJob` 随即返回，空导入队列被清除（`src/renderer/src/views/LibraryView.tsx:4358` 至 `src/renderer/src/views/LibraryView.tsx:4405`）。

当前正在调用的 Paddle batch 可以写入 `batch_queue`，但尚未提交的后续 OCR 批次仍只存在 renderer 的 `autoOcrQueue`。关闭应用后，已经入库但还没轮到的文献不会以原任务顺序和设置自动接续。预览队列同样只在 renderer 内存和 timer 中存在。

**优化方案：**

- 文献标记 stored 的同一提交阶段写入持久化下游任务或 outbox，任务依赖为 `import item -> OCR item -> preview/index`。
- OCR 章节若采用统一 `task_jobs/task_items`，导入不得再建立第二套物理调度器；本章的 job/item 是逻辑模型，最终由全局任务模型承载。
- OCR、预览、元数据提取使用独立并发池和优先级。阅读器按需预览应高于后台批量缩略图，但不能抢占正在写数据库的提交事务。
- renderer 关闭、切换页面或崩溃不影响任务继续；任务中心重新订阅聚合进度即可。

### IMP-P1-05 去重规则可能漏重、误拦合法同名文件并改写已有 PDF 资产

**证据等级：已确认。**

非 PDF 去重只检查当前 renderer 已加载的文献标题和 basename（`src/renderer/src/views/LibraryView.tsx:3995` 至 `src/renderer/src/views/LibraryView.tsx:4022`、`src/renderer/src/views/LibraryView.tsx:4490` 至 `src/renderer/src/views/LibraryView.tsx:4515`）。文库本身按页加载（`src/renderer/src/views/LibraryView.tsx:2264` 至 `src/renderer/src/views/LibraryView.tsx:2305`），因此未加载页中的重复文件会漏过；同名但内容不同的合法资料又可能被直接跳过。

PDF 使用内容 hash 的方向正确，但发现已有文献时，无论原 PDF 是否仍在，都会调用 `restorePdfAssetForDocumentAsync`（`src/main/ipc/documents.ts:3879` 至 `src/main/ipc/documents.ts:3900`）。传入 manual path 后，restore 不走“已有文件直接返回”分支，而是重新复制或压缩并更新 `file_path`（`src/main/pdf-assets.ts:1141` 至 `src/main/pdf-assets.ts:1209`）。当重复文件 basename 不同时，可能留下旧托管 PDF 并把文献指向新副本，界面却提示“未重复导入”。

**优化方案：**

1. 所有支持格式统一使用内容指纹作为 authoritative identity；size/mtime 只能做候选筛选，basename 只能做提示。
2. 同名不同内容默认允许导入，并在重复审查页提示；同内容不同路径合并为一个文献或补充来源记录。
3. 已有 PDF 可读时，重复导入必须是无写入 no-op，只允许新增文件夹关系或来源记录；只有资产缺失时才进入 restore。
4. restore 改变托管路径后，旧托管文件必须在确认无引用后进入可恢复清理任务。
5. 旧 basename 规则保留为兼容提示，不再决定是否丢弃任务。

### IMP-P1-06 已知指纹会关闭复制过程 hash，源文件变化时可能写入错误身份

**证据等级：已确认。**

当 PDF 因同 size 候选而提前计算过指纹时，`copyFileWithFingerprintAsync` 将 `hash` 设为 null，复制期间不再计算实际字节的 hash，最后直接把旧 SHA-256 赋给存档副本（`src/main/pdf-assets.ts:442` 至 `src/main/pdf-assets.ts:499`）。如果外部程序在预 hash 和复制之间替换或修改源文件，数据库可能把新内容记录为旧 hash，破坏重复判断、原件恢复和证据可追溯性。

**优化方案：**

- 复制流始终计算实际写入字节的 SHA-256；已有指纹用于最终比较，不用于关闭 hash。
- 复制前后比较 size、mtime 和文件句柄信息；变化时把 item 标为 `source_changed`，不要提交文献。
- 先写临时文件，校验长度与 hash 后原子 rename 到托管路径。
- 对同路径重试使用 item attempt id，迟到进度不得覆盖新 attempt。

### IMP-P2-01 page_num 没有唯一约束，并发初始化可能产生重复页

**证据等级：已确认。**

`pages` 只有普通 `(doc_id, page_num)` 索引，没有唯一约束（`src/main/database.ts:340` 至 `src/main/database.ts:355`、`src/main/database.ts:932` 至 `src/main/database.ts:937`）。页初始化先读取已有页号，再按块插入并在块间 yield（`src/main/ipc/documents.ts:684` 至 `src/main/ipc/documents.ts:715`）。阅读、预览、OCR 或恢复并发补页时，多个调用可能基于同一旧快照插入相同页号。

**优化方案：**

1. 迁移前生成重复页诊断报告，按 proofed text、有效 OCR、图片存在、OCR 版本和更新时间选择保留行，无法自动合并的进入人工复核。
2. 创建条件唯一索引：同一 doc 的非空 page_num 只能有一行；保留历史上确有用途的 NULL 页号兼容。
3. 页初始化改为幂等 `INSERT ... ON CONFLICT DO NOTHING`，更新使用稳定 page identity。
4. 迁移必须先备份，并在索引创建失败时回滚到原数据库。

这是一项会显著改善正确性的增量迁移，值得实施，但必须等重复数据诊断和恢复演练通过后再批准执行。

### IMP-P2-02 大 JSON、TXT、EPUB 和 PDF 预检仍会整文件进入内存

**证据等级：已确认。**

- JSON 使用 `readFile(..., 'utf-8')` 后一次性 `JSON.parse`，并把所有 page 对象保留在数组（`src/main/ipc/documents.ts:3904` 至 `src/main/ipc/documents.ts:3964`）。
- TXT 先完整 `readFile`，再按换行拆成数组和 sections（`src/main/ipc/documents.ts:2123` 至 `src/main/ipc/documents.ts:2125`、`src/main/ipc/documents.ts:2262` 至 `src/main/ipc/documents.ts:2345`）。
- EPUB 使用 `JSZip.loadAsync(await readFile(filePath))`，并累积全部 sections、spine 和 TOC（`src/main/ipc/documents.ts:2128` 至 `src/main/ipc/documents.ts:2245`）。
- PDF 文本层预检即使只抽样少量页，也先把完整 PDF 读成 `Uint8Array`（`src/main/pdf-preflight.ts:233` 至 `src/main/pdf-preflight.ts:278`）。

此外 TXT/EPUB 在复制后仍解析原始 `filePath`，不是托管副本（`src/main/ipc/documents.ts:3980` 至 `src/main/ipc/documents.ts:3990`），可能出现“存档内容”和“已入库文本”来自不同版本。

**优化方案：**

- TXT 使用流式解码、增量分段和 staging 文件；编码检测只读取有限前缀。
- PDF 预检移到 worker，优先使用文件路径/range 读取能力；如果 PDF.js 仍要求整文件，必须限制同时预检数量并将 RSS 纳入验收。
- JSON 和 EPUB 的完全流式解析可能需要新的成熟依赖。实施前单独提交依赖、许可证、体积和维护评估，由用户确认；未获批准前至少放入受控 worker、从 staging 读取并提供清楚的资源错误。
- EPUB 必须校验 entry 数、声明/实际解压大小、路径穿越和压缩比。安全预算限制单个恶意归档，不限制文献总数。

### IMP-P2-03 PDF 原件仓库索引仍会全量物化，并保留同步/异步两套实现

**证据等级：已确认。**

异步索引会先把所有 PDF 路径收集进数组、读取全部目标文献、全部已有索引行并构造多个 Set/Map，之后才逐文件处理（`src/main/pdf-assets.ts:548` 至 `src/main/pdf-assets.ts:627`、`src/main/pdf-assets.ts:798` 至 `src/main/pdf-assets.ts:879`）。指纹回填也一次性查询全部带文件路径的文献（`src/main/pdf-assets.ts:665` 至 `src/main/pdf-assets.ts:692`）。同一模块还保留递归同步扫描、同步 hash、同步索引、同步恢复和异步版本，增加主进程阻塞和行为漂移风险。

**优化方案：**

- 用游标分页读取目标 hash 和旧索引；目录 walker 发现一项就比对/写入，不保存全部路径。
- 每次索引生成 scan id，在 SQL 中标记 seen，结束后按 scan id 清理未见旧行，避免内存 `matchedPaths` 覆盖全仓库。
- hash worker 数量有界，支持暂停、取消、断点和进度聚合。
- 迁移所有调用方到异步服务后删除同步路径；在确认零调用前保留兼容 wrapper，但 wrapper 不得在 Electron 主线程做同步递归和 hash。

### IMP-P2-04 活跃 OCR 批处理与 legacy batch API 形成两套调度语义

**证据等级：已确认。**

renderer 实际主要调用 `documents:batchOcr`，同时 preload 仍暴露 `batch:start/create/pause/resume/cancel/list`，启动恢复还会执行 `batchProcessor.resumePendingQueueFromDatabase()`。legacy processor 把全部 docIds 保存在 job 中，并一次性读取、分组全部 pending queue rows（`src/main/batch-processor.ts:344` 至 `src/main/batch-processor.ts:363`、`src/main/batch-processor.ts:464` 至 `src/main/batch-processor.ts:516`）。恢复时每个 batch group 都立即启动，没有统一全局并发池。

legacy pause/cancel 只修改内存状态；cancel 还会删除 job，但不会中止当前 AbortController 或可靠更新持久 queue item（`src/main/batch-processor.ts:781` 至 `src/main/batch-processor.ts:802`）。`batch:list` 也不分页返回所有记录（`src/main/ipc/batch.ts:57` 至 `src/main/ipc/batch.ts:63`）。

**优化方案：**

- 模块 03 最终确定唯一任务调度器，导入、手动 OCR、自动 OCR 和恢复共用 claim、lease、attempt、pause/cancel 合同。
- 旧 `batch:*` IPC 先桥接到新服务并保留响应形状；确认 renderer、脚本和插件零旧调用后再弃用。
- pause 停止领取新 item；cancel 必须中止当前网络/worker，并按用户选择保留已完成页或回滚当前 attempt。
- 所有列表按游标分页，聚合统计由 SQL 返回。

### IMP-P2-05 来源、格式和文件夹归属合同不完整

**证据等级：已确认。**

- 文件选择器和目录扫描把 MOBI/AZW/AZW3 列为支持格式，实际导入则固定报“请先转换”（`src/main/ipc/documents.ts:655` 至 `src/main/ipc/documents.ts:664`、`src/main/ipc/documents.ts:3732` 至 `src/main/ipc/documents.ts:3742`、`src/main/ipc/documents.ts:3975` 至 `src/main/ipc/documents.ts:3977`）。
- Paddle JSON 页面图片直接记录 payload 中的原路径，没有按 JSON 所在目录解析相对路径，也没有复制到托管存储；源目录移动、备份恢复或换电脑后版式图片会消失（`src/main/ipc/documents.ts:3942` 至 `src/main/ipc/documents.ts:3957`）。
- JSON 自带 metadata 在系统来源字段之后展开，可以覆盖 `import_source_type`、`original_json_path` 和 `imported_at`（`src/main/ipc/documents.ts:3916` 至 `src/main/ipc/documents.ts:3925`）。
- 文件夹关系写入失败只记录 console error，文献仍被视为成功并从队列移除（`src/renderer/src/views/LibraryView.tsx:4232` 至 `src/renderer/src/views/LibraryView.tsx:4243`）。
- `ImportProgressEvent` 没有 jobId、itemId、attemptId、稳定错误码或 canceled 终态（`src/shared/types.ts:403` 至 `src/shared/types.ts:414`）。

**优化方案：**

1. 选择器只把可直接解析的格式称为“支持”；待转换格式放入明确的转换入口，不进入必失败队列。
2. JSON 外部图片默认复制到托管 staging，支持相对 JSON 路径；“仅链接外部资源”作为显式高级选项并显示可移植性风险。
3. 系统 provenance 字段和导入文件 metadata 分命名空间保存，外部 payload 不能覆盖系统字段。
4. 文件夹关联成为 item 的持久 phase。失败可单独重试，不能被成功 toast 掩盖。
5. additive 扩展进度合同，增加 job/item/attempt、状态、phase、错误码、recoverable 和更新时间；旧字段继续发送一个兼容周期。

### IMP-P3-01 PDF 压缩模块存在未接入的重型路径

**证据等级：已确认调用关系。**

`tryCompressWithRasterRebuild`、`tryRasterRebuildForSmallerPdf` 和 `ensureStoredPdfCompressedForUpload` 当前没有业务调用方；实际导入测试还明确要求 OCR 不调用上传前压缩。同步和异步压缩/复制实现同时存在（`src/main/pdf-compression.ts:333` 至 `src/main/pdf-compression.ts:439`、`src/main/pdf-compression.ts:460` 至 `src/main/pdf-compression.ts:577`、`src/main/pdf-compression.ts:609` 至 `src/main/pdf-compression.ts:660`）。

**优化方案：**

- 在正式实现前以静态调用图、打包产物和回归脚本再次确认零调用。
- 无产品入口的 raster rebuild 和上传前压缩删除或移入实验模块，不继续维护隐形行为。
- 保留 qpdf 的异步“资产恢复时可选压缩”能力；同步 wrapper 在调用方迁移后删除。
- 删除前更新相关源码字符串回归，改成行为测试，避免测试反向锁死死代码。

## 5. 目标任务与数据模型

### 5.1 单一持久化调度模型

```text
ImportJob
  -> Source discovery producer
  -> ImportItem rows in SQLite
  -> bounded claim window
  -> stage/copy/hash/parse
  -> document projection commit
  -> durable downstream task/outbox
       -> OCR
       -> preview
       -> metadata/index
  -> task center aggregates
```

建议逻辑字段：

| 实体 | 必要字段 | 说明 |
| --- | --- | --- |
| job | id、type、status、settingsSnapshot、counts、createdAt、updatedAt | settingsSnapshot 固定本次任务策略，用户之后改设置不改变已开始 item，除非主动“应用到未开始任务” |
| item | id、jobId、ordinal、sourcePath、normalizedPath、folderId、engine、status、phase、attempt、documentId | sourcePath 只在本机数据库和脱敏日志中使用 |
| identity | size、mtime、sha256、storedSha256、sourceChanged | copy 流实际 hash 是最终事实 |
| error | code、message、recoverable、nextRetryAt | UI 按稳定 code 给恢复动作 |
| lease | workerId、leasedAt、leaseExpiresAt、heartbeatAt | 崩溃后可重新 claim，避免双执行 |
| downstream | dependencyItemId、kind、status | 保证导入完成后 OCR/预览不会只留在 renderer 内存 |

物理实现可以是 `import_jobs/import_items`，也可以在模块 03 复核后落为通用 `task_jobs/task_items`。只能有一套实际 claim/lease 调度器，不能让导入和 OCR 各建一套互不兼容的表。

### 5.2 有界资源规则

- 文献总数、待处理 item 总数和任务历史不设置产品上限。
- 路径发现写库块、claim 数、hash worker、解析 worker、OCR 上传、预览渲染和 UI 事件频率分别设上限。
- renderer 只保留可见任务、最近错误和聚合值；详情按游标分页。
- 单个恶意归档的解压安全预算不等于文献数量上限。超大合法文件应顺序处理或落盘，不通过无限内存支持。
- 所有缓存都有容量、TTL、淘汰和观测指标。

### 5.3 文件与数据库提交规则

1. 源文件只读，先复制到 staging。
2. staging copy 同时 hash，完成后校验实际 size/hash。
3. 所有解析从 staging 或已验证托管副本读取。
4. processing 文献不进入普通成品列表；任务中心仍可查看。
5. 终态事务同时完成 document projection、item 状态和下游任务记录。
6. 失败立即补偿，崩溃按 lease/phase 恢复。
7. 最终文件只通过同卷原子 rename 替换；旧资产延迟清理并可恢复。

## 6. 数据库兼容与迁移方案

### 6.1 建议批准的增量迁移

**迁移 A：持久 job/item。**

- 只新增表和索引，不改 `documents`、`pages`、`library_import_queue_state` 的现有列。
- 首次启动若新表无活动任务且旧 snapshot 存在，在事务中逐项展开旧 jobs；成功校验数量、顺序、engine 和 folder assignment 后才标记 legacy migrated。
- 旧 snapshot 至少保留一个兼容版本或保留只读备份，避免升级中断后丢队列。
- 降级旧版本仍能打开文献数据库；旧版本看不到新任务时，升级前必须提示先暂停或导出未完成任务清单。

**迁移 B：page identity 唯一性。**

- 先运行只读诊断和安全备份。
- 自动合并规则必须保留校对文本、有效 OCR、图片、OCR versions 和引用关系；存在冲突时不自动删除。
- 只有重复数为 0 时创建条件唯一索引。
- 迁移脚本以 migration id 记录，可重复运行；任一步失败恢复备份并保留诊断报告。

### 6.2 暂不批准的破坏性变化

- 不重命名或删除 `documents/pages/batch_queue/library_import_queue_state`。
- 不一次性改所有 file_path、metadata 或 snake_case 字段。
- 不把现有 SQLite 替换为服务端数据库。
- 不为了队列重构重新 OCR、重建全部页或重写全部托管文件。

## 7. 分阶段落实方案

### 阶段 A：目标验收和故障注入先行

- 为复制后、document INSERT 后、第 2 个 page chunk、TOC 保存、文件夹关联、最终状态和下游任务写入增加 fault points。
- 建立真实 kill/restart harness、源文件修改 race、磁盘满/权限失败和超大任务基准。
- 记录当前 1 千、10 万、100 万路径的首批启动时间、RSS、SQLite 写入 p95/p99 和恢复时间。
- 此阶段不改变业务行为。

### 阶段 B：共享任务合同和增量 schema

- 在 shared 中定义 job/item/attempt/status/error/progress DTO，旧 ImportProgressEvent 兼容扩展。
- 创建 job/item/lease/downstream 或 outbox 表，并完成旧 snapshot 可重入迁移。
- main 提供分页任务查询、聚合、pause/resume/cancel/retry；preload 只暴露 typed API。

### 阶段 C：流式发现和有界调度

- 目录 walker 边发现边 INSERT，不再返回全部 filePaths。
- scheduler 按用户设置 claim，预取窗口有界；renderer 改为订阅聚合和当前项。
- 保留旧 `resolveImportSources/importDocuments` 作为兼容适配器，小任务仍可使用，新的大任务入口不走全量数组。

### 阶段 D：staging、指纹和幂等导入

- PDF、图片、TXT、EPUB、JSON 分别建立 item processor，共用 staging、copy/hash、source_changed 和补偿框架。
- 所有格式采用内容指纹；修复已有 PDF no-op/restore 分支。
- JSON 图片托管、provenance 命名空间和文件夹 relation phase 同步落地。

### 阶段 E：页面替换保护和唯一索引

- 先实现 page staging/swap 和失败保持旧页的行为测试。
- 运行重复页诊断、人工冲突处理和备份恢复演练。
- 创建条件唯一索引，所有页初始化改为幂等 upsert。

### 阶段 F：持久化 OCR/预览交接与 batch 收敛

- 导入终态事务写下游任务，关闭 renderer 后仍继续。
- 把 `documents:batchOcr` 和 legacy `batch:*` 接到同一 scheduler。
- 验证 pause、cancel、重启恢复、部分页保留和用户并发设置。

### 阶段 G：大文件和原件仓库规模化

- TXT 流式解码；PDF preflight worker/range 基准；原件仓库流式索引和 scan id 清理。
- JSON/EPUB 流式依赖候选先提交用户审批，再决定采用新依赖还是受控 worker 降级。
- 删除确认无调用的同步和 raster 压缩路径。

### 阶段 H：任务中心和兼容清理

- 提供任务、失败、重复、来源和恢复操作，不用大量 toast 代替任务历史。
- 经过至少一个兼容版本、遥测/诊断和回滚演练后，停止写 legacy snapshot；保留旧读取导入器。
- 更新开源教程、故障报告模板、数据库规范和最终验收脚本。

每个阶段独立提交。正式业务代码修改前，按总章程创建 checkpoint 提交和标签；任何新依赖在对应阶段开始前单独征得用户确认。

| IMP-16 | PDF 原件仓库 10 万文件索引内存有界、可取消、可断点 | scan id、分页、取消、重启测试 | 现有仓库路径和索引表可迁移 |
| IMP-17 | 旧 state_json 和含重复 page 的数据库可安全升级、重复执行和恢复 | migration + backup restore 测试 | 不破坏旧数据库主体 |

性能阈值在阶段 A 用同一台基准机固定。建议最低目标是：10 万路径扫描时 renderer 不接收超过 500 项的详情页；主进程额外 RSS 不随剩余 item 数线性增长；复制/hash 缓冲总量由 worker 数乘固定块大小决定。若基准证明绝对阈值需要调整，必须保留“有界且首批无需等待全量枚举”的行为要求。

## 9. 新功能方向

### 9.1 导入任务中心

提供持久任务列表、当前阶段、速度、预计剩余、失败原因、重试、跳过、暂停、恢复、取消和错误清单导出。它是任务状态的真实入口，toast 只做短提示。用户可以关闭文库页面或重启应用后继续查看同一任务。

### 9.2 导入前清单与干运行

在不复制文件的情况下流式生成清单，统计格式、大小、重复、缺失资源、预计 OCR 页数、磁盘空间和目标文件夹。用户可过滤格式、排除目录和保存本次规则。大目录不需要等待全部扫描完才展示前几批结果。

### 9.3 重复审查与来源谱系

对同内容不同路径显示来源列表，对同名不同内容提供并排元数据和首页预览。每篇文献记录首次来源、后续补回来源、fingerprint、导入时间和任务 ID，便于研究引用、资产找回和问题追踪。

### 9.4 文件夹级导入配置

允许文件夹保存默认 OCR 引擎、古籍/论文模式、自动 OCR、预览优先级、标签和元数据策略。任务创建时把配置快照写入 job，保证批量任务中途修改全局设置不会造成前后行为不一致。

### 9.5 监视收件箱

可选监视一个“待整理”目录，新文件稳定写入后自动进入导入清单，但默认要求用户确认，不静默删除或移动源文件。若采用可靠跨平台 watcher 依赖，必须先提交依赖审批；未批准时可用手动“重新扫描”实现第一版。

## 10. 依赖、风险与审批

- 持久化调度、staging、hash、worker_threads、游标分页、outbox 和任务中心核心方案不需要新增依赖。
- TXT 流式处理可使用 Node 标准 streams/TextDecoder 实现。
- 大型 JSON 的通用流式 parser、EPUB 流式 zip reader 和可靠目录 watcher 可能需要新增依赖。正式选型前必须列出许可证、维护活跃度、安装体积、Electron 打包兼容、安全历史和无依赖回退方案，并由用户确认。
- page 条件唯一索引和 job/item 表属于增量数据库迁移。本章认为收益足够显著，原则上批准进入实施计划，但执行前仍必须完成备份、诊断、可重入迁移和恢复演练。
- 路径、文件名和文献内容属于隐私数据。任务中心、日志和诊断包只显示必要 basename 或脱敏路径，详细路径只在用户主动展开时显示。

## 11. 与其他模块的兼容约束

- 模块 03 OCR 必须复用本章的 job/item/attempt、lease、pause/cancel 和下游依赖模型，不能再新增第三套队列。
- 模块 04 文库和文件夹必须从 SQL 聚合/分页读取任务与文献，不通过 renderer 已加载页做 authoritative 去重。
- 模块 05 阅读器只能读取 committed page set；page generation 切换时保持当前 locator 可解释并提示内容版本变化。
- 模块 06 检索只索引 committed generation；失败 staging 和 processing 文献不得进入正式命中。
- 模块 07 AI 只能引用已提交、可定位和带 provenance 的文本，不读取导入中间态。
- 模块 11 数据库与备份必须包含新任务表、staging 清单和迁移状态，但备份恢复后不能自动访问不存在的旧绝对路径。
- 模块 12 发布与测试必须把真实 kill/restart、大规模队列、磁盘故障和源文件变化纳入新版验收。
- 导入优化不得通过限制文献总数、无限提高并发、静默跳过失败文件或降低 fingerprint 校验来换取速度。
