# 12 性能、稳定性、测试与开源发布

## 1. 本章结论

当前仓库已经具备 Windows 构建、62 段默认检查、Electron smoke、Apache-2.0 项目许可证、QPDF 随包运行时、开源卫生检查和 GitHub Release 自动化，`package-lock.json` 也处于可复现的 lockfile v3 状态。2026-07-10 的只读结构检查得到 732 个包条目，未发现缺失 license、registry 外 resolved、缺失 integrity 或多版本同名包；当日 `npm audit` 与 `npm audit --omit=dev` 均报告 0 个已知漏洞。这些基础应保留。

但当前状态**不能公开发布**。首要阻断不是代码风格，而是 9 张已跟踪 README 截图来自实际文库：可读到真实书名、摘录、检索历史和正文，`screenshot-06-layout-restore.png` 直接显示 `z-library.sk/lib.sk/Z-lib.sk`，`screenshot-08/09` 显示 JSTOR 正文及下载 IP。当前 `check:opensource` 只扫描文本，完全看不到这一泄漏面。Release 又会在 tag push 或手工 dispatch 后自动创建公开 Release，没有本地用户批准、draft、environment approval 或发布前安装包验收。

发布链还有四个实质缺口：CI/Release 都先 build/package 后 check；三个台账已知失败不在默认门禁；Electron smoke 启动源码工作树而非安装包/便携包；现有 1.0.9 包中没有项目 `LICENSE`、`NOTICE`、`THIRD_PARTY_NOTICES.md`，只有 Electron/Chromium 和各 npm 包自己的许可证。性能方面只有无阈值的尺寸打印，没有固定机器/fixture、event-loop、RSS、IPC、数据库、故障注入或迁移恢复基线。

因此本章建议先冻结公开发布并替换真实截图，再把流程改为“固定环境 -> 验收 -> 构建 -> 安装/便携验证 -> 许可证/SBOM/摘要 -> 本地用户批准 -> 可选签名 -> 明确公开”。任何新工具、SaaS、签名证书、远端 Actions 或 Release 都必须另行获得用户确认。

```text

  typecheck -> 61 个 npm 子命令串行执行
  不含 smoke、test:search、metadata-tags、OCR recovery/PDF resume、startup recovery、reader-state

  checkout -> Node 20 -> npm ci -> build -> check

  tag push / workflow_dispatch -> npm ci -> build:win
```

## 4. 关键问题

### D12-P0-01 已跟踪发布截图泄露实际文库内容并含来源/版权风险标识

**证据等级：已确认。** `README.md:5-23` 公开引用 9 张大图；逐图可见真实书名、摘录、搜索历史、正文和页码，`screenshot-06` 含 z-library 域名，`screenshot-08/09` 含 JSTOR 下载 IP。`SECURITY.md:20-24` 与 `docs/ARCHITECTURE.md:26-31` 明确禁止提交真实文献/OCR/截图私密内容；`check-opensource.js:35-50` 仅扫描文本扩展，`:236-258` 不检查 PNG。

**影响：** 公开仓库/Release 可能持续传播用户研究足迹、受限文献正文和来源标识；常规文本门禁会绿灯。若历史已公开，仅删除当前文件也不能撤回历史暴露。

**方案：** 立即把当前 commit 标记为禁止公开；用许可明确的合成 fixture 重建 9 张图，扫描 EXIF/text/OCR 与可见内容；由用户决定是否进行历史清理、远端下架或版权/隐私处置。任何远端动作必须再次批准。

### D12-P1-01 Release 自动公开，绕过本地用户批准

**证据等级：已确认。** `.github/workflows/release.yml:3-15` 接受 tag push/手工输入并获得 contents write；`:64-98` 直接 `gh release create` 和 `upload --clobber`，无 draft、GitHub Environment、审批人或本地验收 token。

**影响：** 一次 tag push 即可公开未获批准的代码和 exe；失败可能留下空 Release，重跑又覆盖同名资产。

**方案：** 拆为不可公开的候选构建与独立 publish job；默认只上传 Actions artifact。publish 需要受保护 environment、明确 tag/commit/manifest、本地用户书面批准，先 draft，资产/摘要完整后再显式公开。

### D12-P1-02 CI/Release 顺序反了，且打包后没有成品验收

**证据等级：已确认。** CI 在 `ci.yml:24-31` 先 build 后 check；Release 在 `release.yml:48-55` 先 `build:win` 后 check。`package.json:90-91` 的 Windows 构建不含 check/smoke；`smoke` 是独立命令（`:32`）。

**影响：** 已知错误仍消耗打包时间；check 通过也不能证明 app.asar、NSIS、portable、qpdf、迁移、卸载或许可证内容可用。

**方案：** 顺序改为 fast check -> integration -> UI E2E -> build -> unpack inspection -> installed/portable smoke -> license/SBOM/hash -> approval -> publish；后续阶段只消费同一候选 commit 和不可变产物。

### D12-P1-03 三个已知失败不在默认 check，绿色门禁会掩盖真实回归

**证据等级：已确认。** 台账 `00-代码审阅台账.md:298`、`:304`、`:318` 分别标记 `ocr-async-pdf-complete-pending-regression.js`、`ocr-pdf-resume-regression.js`、`reader-state-smoke.js` 当前失败。PDF resume 只有 `test:ocr-pdf-resume`（`package.json:84`）且不在 `check:33`；另两个没有默认 npm 门禁。

**影响：** OCR 完成态、断点恢复和阅读状态可能在发布时仍坏；Release 的 check 仍可通过。

**方案：** 先固定失败 fixture 和期望，修复或建立有负责人/到期日的临时 quarantine；发布门禁要求三者通过，禁止永久忽略或仅从文档删除。

### D12-P1-04 安装包没有项目 LICENSE/NOTICE/THIRD_PARTY，VC++ 许可闭包也不完整

**证据等级：已确认。** `package.json:182-191` 只打入 out/resources/vendor；现有 1.0.9 app.asar 没有三份根文档。Apache-2.0 `LICENSE:89-121` 要求分发许可证并保留适用 NOTICE；`THIRD_PARTY_NOTICES.md:23-30` 只写 Microsoft terms 名称，没有条款/来源证据。

**影响：** 源码仓库合规不等于二进制分发合规；安装/便携用户无法在离线包内读取项目和第三方归属。

**方案：** 将 `LICENSE`、`NOTICE`、`THIRD_PARTY_NOTICES.md` 与机器生成依赖清单放入包内固定路径并在 About/设置页可达；补齐 VC++ redistributable 来源、版本、允许再分发证据，由用户/法律责任人审批后再发。

### D12-P1-05 tag、package、changelog 与产物没有同一版本原子合同

**证据等级：已确认。** Release 只检查字符串以 `v` 开头（`release.yml:32-46`）；没有比较 `package.json:3`、lock 根版本和 CHANGELOG 首节。`gh release create` 先于资产枚举/上传（`:75-98`），重跑使用 `--clobber`。

**影响：** 可把 1.0.9 exe 放到其他 tag，或创建公开但无资产的 Release；同名资产可被静默替换，校验值失效。

**方案：** 严格 semver；要求 tag=`v${package.version}`、lock 与 changelog 同版、tag 指向候选 SHA；先计算资产清单/摘要，再创建 draft；公开资产禁止 clobber，重发必须新版本。

### D12-P1-06 Electron smoke 验证源码工作树，不验证安装版或便携版

**证据等级：已确认。** `electron-smoke.js:1545-1562` 以参数 `.` 启动 Electron，虽隔离 `GUJISMART_DATA_DIR/PROFILE_DIR`，但不是 dist exe；`:1564-1609` 覆盖导航、搜索与阅读，`:1610-1612` 仅关闭应用，没有删除三个 temp 根目录。

**影响：** main/renderer 源码可通过，asar/native module/qpdf/安装数据目录仍可能失败；CI 不运行 smoke，失败也没有 trace/screenshot/日志 artifact。

**方案：** 保留现有源码 smoke 为快速层，新增 win-unpacked、NSIS 静默/交互安装和 portable 三个成品 smoke；每次使用唯一合成目录，finally 清理，失败上传脱敏 trace/日志。

### D12-P1-07 没有固定性能与稳定性基准，无法阻止卡顿、内存和数据库回归

**证据等级：已确认。** `report-build-size.js:4-13` 只列路径，`:85-107` 只输出数字；OCR benchmark 只覆盖单一 fixture。当前没有 event-loop delay、renderer/main RSS、IPC payload/latency、SQLite p95/busy、长任务取消/恢复或故障注入门禁。

**影响：** 代码可在功能断言全绿时出现 UI 冻结、RSS 持续增长、IPC 大对象复制、数据库长事务或大库退化。

**方案：** 固定 Windows/Node/Electron/硬件档位与合成规模，输出可比较 JSON；先采用当前 commit 基线加 5% 回归阈值，再按第 6 节目标逐步收紧。性能失败不得靠删除样本解决。

### D12-P2-01 默认 check 过度依赖源码字符串，结构绿灯不等于行为正确

**证据等级：已确认。** `folder-management`、`library-import-queue-persistence`、`document-delete-resilience`、`onboarding` 等大量使用 `source.includes`/正则；`function-contract-regression.js` 同样验证 API 名称存在。只有部分共享 helper、SQLite/Electron/search 脚本执行真实行为。

**影响：** 注释、死代码或同名字符串可让检查通过；等价重构会产生假失败；竞态、回滚、错误路径没有执行。

**方案：** 先保留这些形状护栏，再逐项建立 contract/integration/E2E 行为测试；每个替代测试标注覆盖等价后才删除旧断言。

### D12-P2-02 mojibake 与 opensource 门禁覆盖范围不闭合

**证据等级：已确认。** `check-mojibake.js:6-13` 只扫 README、package 和 main/shared/renderer，漏 preload、scripts、CHANGELOG、其余 docs/workflow；`check-opensource.js:31-50` 排除 lock 且只读有限文本扩展，`:140-157` 按工作树遍历而非 Git tracked manifest。

**影响：** 图片、PDF、ICO、DLL/EXE、未知扩展、文档和 Git 历史中的隐私/许可证问题不被拦截，本次 P0 即实例。

**方案：** 以 `git ls-files -z` 为输入；文本做 UTF-8/secret/path，图片做尺寸/EXIF/OCR 人工复核，二进制做 allowlist/hash/license/provenance；生成可审计 manifest，敏感命中只在本地显示脱敏摘要。

### D12-P2-03 生产依赖边界与包体没有预算

**证据等级：已确认。** 两个 `@types` 在生产 dependencies（`package.json:113-114`），app.asar 样本 175.47 MiB；`sync-pdfjs-assets.js:25-26` 复制整套 cmaps/standard_fonts；QPDF manual 和当前未调用的两个工具也随包。

**影响：** 安装包、解压体积、启动 I/O、审计闭包持续扩大，且无回归失败。

**方案：** 把纯类型包移到 dev；以实际运行 import 构建生产 allowlist；保留 PDF.js 必需字体/映射和 QPDF 必需文件；设置 app.asar、renderer chunk、installer/portable 的绝对与相对预算。

### D12-P2-04 QPDF 版本/来源/运行选择没有机器可验证合同

**证据等级：已确认。** notices 的 12.3.2 是“based on included documentation”（`THIRD_PARTY_NOTICES.md:12`）；QPDF PE 无版本字段且未签名；运行时 bundled 缺失会静默执行 PATH 上 `qpdf`。

**影响：** 构建者无法证明 binary 与 notice 对应；安装损坏或 PATH 劫持时可能运行非候选程序，结果和安全边界不可复现。

**方案：** 维护 vendor manifest（上游版本/URL/hash/license/文件用途），CI 对 bundled hash 和最小文件集做离线校验；生产默认不静默回退 PATH，若保留外部 qpdf，必须用户显式选择并显示版本/路径摘要。

### D12-P2-05 GitHub Actions 使用可移动 tag，Release 写权限范围过宽

**证据等级：已确认。** checkout/setup-node/upload-artifact 使用 `@v6/@v7`（`ci.yml:15-22`、`release.yml:23-30,57-62`），未固定 commit SHA；`contents: write` 位于 workflow 全局（`release.yml:14-15`）。

**影响：** 第三方 Action 上游 tag 改变会改变构建；所有 release job 步骤都继承写权限。

**方案：** 固定审核过的 Action SHA并记录版本注释；构建 job 只读，publish job 才给 contents write，并受 environment 审批。

### D12-P2-06 开发/发布文档存在事实冲突与缺失

**证据等级：已确认。** README `:43-45` 引导下载 Release，教程 `:21-36` 又称只提供源码、由维护者本地另发；README `:70` 称构建后用 Electron userData，而 installer `:28-36` 会把旧 AppData DB 复制到安装目录。`SECURITY.md:9-18` 没有明确私密邮箱/表单、确认时限和响应范围。

**影响：** 用户不清楚下载、数据位置、升级/卸载和漏洞报告渠道；发布说明容易与实际包漂移。

**方案：** 从 package/build/runtime 生成单一发布事实页，明确支持的 Windows/Node、数据目录矩阵、安装/便携差异、升级/卸载和私密安全联系入口。

### D12-P2-07 默认门禁串行且缺少统一报告、超时和失败证据

**证据等级：已确认。** `package.json:33` 把 62 个命令串成一个 shell 链；首个失败后后续不运行。Electron/search 脚本自行管理 temp、退出码和 console，没有统一 JUnit/JSON、超时、重试分类或 artifact。

**影响：** CI 时间增长、后续失败不可见，偶发失败难复现；临时目录可残留并消耗磁盘。

**方案：** 按 fast/integration/e2e/release 分层并允许安全并行；每层统一超时、随机种子、JSON/JUnit 和脱敏 artifact；重试只用于识别 flaky，不把重试通过当稳定通过。

### D12-P3-01 缺少合成研究库与截图生产线

**证据等级：已确认。** 现有搜索 accuracy JSON 是很好的可公开 fixture 起点，但 README 截图来自实际文库，教程图又由空库手工生成。

**影响：** 截图、E2E、性能和文档无法共用确定性数据，容易再次泄漏或漂移。

**方案：** 建立许可清晰、固定 seed 的古籍/论文双 fixture，生成文库、摘录、搜索、OCR、翻译、引用和故障状态；截图仅从该 fixture 产生并带 manifest。

### D12-P3-02 缺少本地 Release Candidate 清单与趋势视图

**证据等级：已确认。** 现有输出分散在 console、dist 和 workflow，没有一份把 commit、版本、验收、性能、SBOM、hash、签名状态和用户批准绑定起来的只读清单。

**影响：** 用户难以判断“这个 exe 是否就是测过的那个”，历史回归也不能比较。

**方案：** 生成本地 `release-manifest.json`/Markdown 和趋势报告；只记录合成数据指标和 hash，不上传用户文档、路径、标题或日志正文。

## 5. 目标性能、稳定性、测试与发布架构

```text
固定工具链 + 固定 seed 合成库
        |
        +-> fast: type/AST/pure unit/UTF-8/tracked-file hygiene
        +-> integration: IPC + SQLite + worker + qpdf + migration + fault injection
        +-> UI E2E: source app（快速）+ win-unpacked（候选）
        +-> performance: event-loop/RSS/IPC/DB/build-size JSON budget
        |
        v
全部验收通过 -> 构建一次 -> NSIS + portable + SBOM + licenses + SHA-256
        |
        v
全新安装/升级/卸载保留/portable smoke -> 本地 RC manifest
        |
        v
用户本地验收并明确批准 -> 可选签名审批 -> draft -> 显式公开
```

固定基准首版采用 Windows 11 x64、CI Node 20、仓库锁定 Electron 39、8 核/16 GiB/SSD 参考档；fixture 至少包含 1k、10k、100k 文献元数据档、10/200/1000 页 PDF 档和古籍/论文双样本。文献数量不设产品上限，100k 只是可重复门禁规模。

目标预算是新版验收目标，不声称当前已达到：

- 交互期间 main/renderer event-loop delay p95 <= 50 ms，除明确后台阶段外单次 block <= 200 ms。
- 空库稳定后 renderer RSS <= 350 MiB；10k 库阅读/搜索峰值 <= 1.2 GiB，任务完成 5 分钟后回落到峰值的 80% 以下；更大规模记录趋势而不以 OOM/崩溃结束。
- 小型 IPC p95 <= 100 ms，分页/搜索 IPC p95 <= 500 ms；默认响应分页且单 payload <= 2 MiB，大对象走文件/流/worker 边界。
- 10k 库常用 DB 读 p95 <= 200 ms、列表/全文搜索 p95 <= 500 ms；busy 有界重试、取消可达，写事务不跨网络/OCR。
- app.asar、最大 renderer chunk、NSIS/portable 先以同 commit 基线 +5% 为阻断阈值；每次优化后只向下收紧。

## 6. 分阶段落实方案

### 阶段 A：发布冻结与隐私/许可证止血

替换 9 张真实截图；建立 tracked binary/image allowlist；确认历史暴露处置；把项目 LICENSE/NOTICE/THIRD_PARTY 和 VC++ 证据放入包；在完成前禁用公开 publish 路径。回退是恢复非公开候选构建，不恢复真实截图或自动公开。

### 阶段 B：测试目录与已知失败清零

给 82 个 npm script 建 owner/tier/timeout/fixture 表；把三个已知失败纳入 mandatory；区分源码形状、纯单元、SQLite integration、Electron E2E 和 manual；统一 JSON/JUnit。回退时保留旧字符串护栏，不能删除行为覆盖。

### 阶段 C：性能与资源预算

固定环境/seed，采集 event-loop、RSS、IPC、DB、启动、导入、搜索、OCR 保存和 build size；先冻结基线和 +5% 阈值，再针对 DocumentView、PDF.js、生产依赖和大 payload 优化。指标采集失败即基准失败，不得当作 0。

### 阶段 D：故障、迁移和 Windows 成品

加入 DB busy/损坏索引、磁盘满/权限拒绝、qpdf 缺失/超时、worker crash、强退、网络中断、旧 schema/旧数据目录 fixture；验证 NSIS 新装/升级/卸载保留与 portable。只使用复制的合成库，绝不连接真实用户库。

### 阶段 E：供应链与候选清单

生成 production SBOM、许可证报告、vendor manifest、SHA-256 和 release manifest；固定 Actions SHA，分离 build/publish 权限；禁止同 tag clobber。任何新增扫描器/Action/SaaS 先由用户审批许可证、维护和数据外传。

### 阶段 F：本地用户验收与受控公开

向用户提供同一候选 commit 的 Setup/Portable、启动方式、REL 矩阵、已知限制、回退和 hash；收到明确“本地测试通过并批准公开”后，才允许可选签名和 draft/public Release。没有批准时只保留本地产物，不 push/tag/Actions/Release。

## 9. 新功能建议

### D12-NF-01 合成研究库与文档截图生成器

**MVP：** 固定 seed 生成古籍/论文、OCR 块、摘录、专题、引用和搜索命中，许可证清晰；一条本地命令重建 README/教程截图并输出 image manifest。

**验收与回退：** 同 seed 的 DB/图片 hash 可重复，截图 OCR 不含真实路径、IP、Key、域名或用户题名；关闭生成器不影响业务数据库，失败只删除临时 fixture。

### D12-NF-02 本地 Release Candidate 检查器

**MVP：** 汇总 commit/version、REL 状态、性能 JSON、SBOM、licenses、vendor/asset hash、签名状态、Setup/Portable 路径和回退说明，不执行上传。

**验收与回退：** manifest 能从产物离线重算，任一缺项即 non-releasable；移除功能只失去报告，不改变产物或用户数据。

### D12-NF-03 性能与稳定性时间序列

**MVP：** 本地保存固定 fixture 的 event-loop/RSS/IPC/DB/build-size JSON，按 commit 比较中位数和 p95；不采集真实标题、路径、正文或遥测。

**验收与回退：** 同机重复波动在约定容差内，回归可定位到指标/场景；关闭后回到单次 JSON 门禁，不影响业务功能。任何云趋势服务必须另行审批。

## 10. 依赖、发布与审批

- 阶段 A-D 可用现有 Node、TypeScript、Playwright、Electron、SQLite、PowerShell 和 GitHub Actions 完成；第一版不新增运行时依赖。
- SBOM/license 工具、secret/image OCR 扫描器、性能采样包、VM 服务、代码签名证书/时间戳服务均属候选，实施前必须向用户说明许可证、维护者、包体、数据外传、费用和无工具替代方案并获得批准。
- 代码签名不是 MVP 阻断；未签名包必须如实标识。采购、导入私钥、上传 secret、调用时间戳服务都需单独审批，私钥不得进入仓库或日志。
- 依赖漏洞例外必须写明 CVE、实际可达性、临时缓解、负责人和到期日；critical/high 默认阻断。0 漏洞是候选 commit 的时点事实，不是永久保证。
- 发布候选只能使用合成数据。真实用户库只允许用户在本机副本上人工验收，日志/trace/截图不得包含路径、题名、正文、Key 或数据库。
- 本章没有批准 push、PR、tag、Actions、Release、SaaS、证书或新依赖。只有用户完成本地验收并明确批准公开后，才可另行执行。

## 11. 与其他模块的约束

- **模块 01：** 统一 TaskState/error envelope 与 worker 边界是可测性前提；性能采样不得把第二套业务状态写回数据库。
- **模块 02：** 导入不限文献总数，但并发、队列、IPC payload 和内存有界；安装/便携必须验证文件复制与原件不变。
- **模块 03：** 三个已知失败先清零；OCR/qpdf 故障注入保留原 PDF、页坐标、人工校对优先和可恢复状态。
- **模块 04：** 1k/10k/100k fixture 覆盖文件夹、标签、分页和缓存失效，不用 renderer 全库物化换取 benchmark 好看。
- **模块 05：** packaged UI E2E 覆盖 PDF/图片/EPUB、阅读状态、原图补回和版式；真实文献不得成为 fixture。
- **模块 06：** 搜索 accuracy、迁移、atomic swap、auto rebuild 与 p95 同时验收；性能优化不能降低证据/locator 正确性。
- **模块 07：** AI/OCR 外部调用在自动门禁中使用 stub；任何联网验收需用户批准且不得发送真实文献，输出保留来源完整性。
- **模块 08：** 所有截图从合成 fixture 生成；固定桌面/窄窗/200% zoom，视觉通过不能替代键盘与语义验收。
- **模块 09：** E2E 覆盖标签/分组/恢复、快捷键、拖拽与 latest-request-wins；测试不得依赖任意 sleep 作为唯一同步。
- **模块 10：** 翻译、引用、导出使用合成文本并检查长内容、来源 hash 和 round-trip，不把受限论文正文提交为 golden。
- **模块 11：** 迁移、备份、恢复、安装升级和卸载保留共用同一 fixture/manifest；任何破坏性演练只对临时副本执行。
- **模块 13/14：** 新功能进入路线图前必须指定 REL 场景、性能预算、依赖/许可、回退与发布审批；全局复核以本章不可公开条件为硬门禁。

本章没有要求立即重写测试框架或替换发布平台。正确顺序是先消除真实截图和自动公开风险，再让现有脚本获得清晰分层与成品证据，最后才讨论新增工具、签名和公开发布。
