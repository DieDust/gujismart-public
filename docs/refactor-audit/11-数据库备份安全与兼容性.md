# 11 数据库、备份、安全与兼容性

## 1. 本章结论

GujiSmart 已经具备 SQLite WAL、外置页面大字段、轮换备份、导入前安全副本、启动恢复、数据库维护状态和文件访问白名单等基础能力。这些能力说明当前数据库不需要为了重构而整体替换，也不应把现有用户库强制迁移到另一种数据库。

当前最高风险集中在“文件系统操作与数据库状态不是同一个事务”：备份恢复会先关闭数据库并依次替换 `db`、`storage`，失败时没有自动回滚；自动备份瘦身会先删除全部轮换槽位，再尝试生成新备份；renderer 还能把任意路径写入文献/页面字段并借读取接口加入本地资源白名单，删除文献又会递归删除未证明属于应用托管区的外部路径；启动恢复也可能在正常导入尚未写入文献行时，把正在使用的 storage 目录当成孤立目录删除。这些都不是界面问题，而是需要先于大规模功能重构修复的数据安全边界。

本章建议第一阶段继续使用现有 SQLite、现有表和现有文件目录，通过在线快照、暂存目录、原子切换、恢复日志、任务互斥和兼容读取提高可靠性。新增表或列不是第一阶段前提；如果后续为了持久化任务租约或迁移日志确需加表，必须按“新增旁路结构、旧库可读、自动备份、事务、失败回滚”执行。

## 3. 当前数据流

### 3.1 手动与自动备份

```text
renderer 设置页
  -> backup:create / backup:runAutoNow
  -> saveDatabase() 执行 PASSIVE WAL checkpoint
  -> 同步递归复制 data/db 与 data/storage
  -> 生成 manifest.json
  -> 手动备份再压缩为 zip；自动备份直接写入 slot-N
```

自动备份默认保留 1 至 3 个槽位。关闭“包含完整 storage”时，仍会保留 `storage/page-payloads`，这对外置 OCR、版式、翻译和 AI 布局结果的可恢复性是正确的。

### 3.2 备份导入与恢复

```text
选择 zip/旧目录
  -> 解压到系统临时目录
  -> 检查数据库存在、外置 payload 引用存在、文件数量和总字节
  -> 在 data/pre-import-backups 创建当前数据安全副本
  -> closeDatabase()
  -> 删除并复制 data/db
  -> 删除并复制 data/storage
  -> 再次比较文件数量与总字节
  -> 返回成功并重启应用
```

当前流程有安全副本，但安全副本只作为人工恢复材料；代码没有在安装新数据失败时自动恢复原目录，也没有重新打开旧数据库。

### 3.3 外置页面大字段

```text
OCR/校对/AI 布局/翻译结果
  -> 超过字符阈值
  -> SHA-256 内容寻址
  -> gzip JSON 写入 storage/page-payloads/objects/<prefix>/<hash>.json.gz
  -> SQLite 保存 page-payload:v2:<relative-path> 引用
  -> 读取时同步解压并回填字段
```

该设计避免把大量 OCR JSON 和文本长期堆在 SQLite 行内，方向正确。当前缺口是最终文件写入不经过临时文件原子替换，读取时也没有验证文件内 SHA-256；缺失或损坏时返回 `null`，调用方可能继续把占位内容当成空文本。

### 3.4 启动恢复

```text
窗口 ready-to-show 后
  -> 恢复 OCR 状态
  -> 重置搜索、AI 布局和翻译的 processing 状态
  -> 修复中断导入和 PDF 压缩源
  -> 修正完成文献与待重建索引
  -> 删除旧临时目录和“孤立” storage 目录
  -> 接续删除任务和持久化批处理队列
```

恢复在窗口已经可操作后运行，改善了启动速度，但也意味着恢复任务必须与新导入、OCR、删除、备份和维护共享明确的任务锁。当前只有启动恢复自身的运行标志和取消位，没有跨领域存储租约。

### 3.5 数据库维护与健康报告

- 旧 ngram 索引按批次删除并在批次间让出事件循环。
- 大页面字段按批次外置，维护状态写入 settings。
- `VACUUM`、存储诊断和外置文件扫描仍在主进程同步执行。
- 健康报告放入 worker，但一次性读取、构建并返回全部文献健康行。

## 4. 关键问题

### D11-P0-01 备份恢复失败时可能留下部分替换的数据，并让当前进程失去数据库连接

**证据等级：已确认。**

`importBackupFromPath` 在创建安全副本后关闭数据库，再依次替换 `db` 和 `storage`（`src/main/backup.ts:518` 至 `src/main/backup.ts:525`）。任何复制或恢复后校验失败都会进入 catch，但 catch 只抛出错误，没有把安全副本自动恢复，也没有重新初始化旧数据库（`src/main/backup.ts:536` 至 `src/main/backup.ts:540`）。IPC 只有成功时才安排重启（`src/main/ipc/settings.ts:1079` 至 `src/main/ipc/settings.ts:1088`）。

可能结果包括：

- 新数据库配旧 storage，或旧数据库目录已删除但新目录只复制了一部分。
- 当前进程的数据库已经关闭，恢复失败后继续使用软件会出现“数据库未初始化”。
- 用户虽有安全副本路径，但必须手工判断和恢复。

**落实方案：**

1. 所有恢复内容先安装到 `data/.restore-staging/<operation-id>`，不直接覆盖当前目录。
2. 在 staging 中打开 SQLite 为只读，执行 `PRAGMA quick_check`、Schema 兼容检查、外置引用核对和 manifest 哈希校验。
3. 获取全局存储维护锁，暂停导入、OCR 保存、索引写入、翻译、删除和备份任务。
4. 关闭数据库后，把当前 `db`、`storage` 原子重命名到同一文件系统内的 rollback 目录。
5. 将 staging 原子重命名为正式目录，重新打开数据库并执行第二次校验。
6. 任一步失败都自动恢复 rollback 目录、重新打开旧数据库并返回稳定错误码。
7. 只有新库重新打开且校验通过后才删除 rollback 目录并重启。

第一阶段不需要数据库迁移，也不需要新增依赖。

### D11-P0-02 “瘦身自动备份”先删除全部轮换备份，再创建一份新备份

**证据等级：已确认。**

`compactAutoBackups` 先递归删除整个 `auto-backups` 根目录，再调用 `runAutoBackupNow`（`src/main/backup.ts:650` 至 `src/main/backup.ts:674`）。如果磁盘已满、文件被占用、数据库 checkpoint 失败或复制中断，旧槽位已全部丢失。界面提示却写成“只会压缩轮换槽位中的旧备份”（`src/renderer/src/views/SettingsView.tsx:2470` 至 `src/renderer/src/views/SettingsView.tsx:2477`），没有说明会先删除所有槽位。

**落实方案：**

- 在现有根目录外先生成并验证一个新的候选槽位。
- 候选成功后，按 `slot-new -> slot-1`、旧槽位顺延的方式原子轮换。
- 任何失败都保留全部旧槽位。
- “瘦身”改为明确策略：保留最新 N 份完整快照；如要去除可再生缓存，必须生成新的备份类型和清晰清单，不能修改旧备份原件。

### D11-P0-03 renderer 可自行授权任意本机文件或目录进入资源白名单

**证据等级：已确认存在直接利用链。**

`documents:import` 对 renderer 提交的路径先直接调用 `allowFileAccessPaths`（`src/main/ipc/documents.ts:3811` 至 `:3812`）；PDF 仓库的 set/index/restore 也直接授权 renderer 参数（`:5200` 至 `:5212`）。`documents:update` 可无 containment/capability 校验写入任意 `file_path/thumb_path`（`:4491` 至 `:4535`），随后 get/getLight/getReadingWindow 会把数据库路径加入白名单（`:4285` 至 `:4294`、`:4335` 至 `:4344`、`:4464` 至 `:4471`）；`pages:update` 对 `image_path` 也存在同类写入（`:5248` 至 `:5268`）。因此 renderer/XSS 可以把任意本机文件甚至目录根暴露给 local-resource 协议，原 D11-P2-03 的“当前无直接利用证据”判断不成立。

**落实方案：** 由 main 文件对话框签发 opaque `FileCapability`，绑定 realpath、用途、读写方向、TTL、一次/多次消费和大小/类型预算；renderer 只能提交 token，不能自行声明路径。每次消费重新校验 symlink、目录边界与用途；数据库只保存规范化路径和 `managed|external|repository` ownership。旧路径兼容读取先进入诊断/重新授权，不自动扩大白名单。

### D11-P0-04 删除文献可递归删除任意外部目录

**证据等级：已确认存在完整写入到删除链。**

后台清理对任务路径直接执行 `rm(path, { recursive: true, force: true })`（`src/main/ipc/documents.ts:246` 至 `:250`）。`getDeleteCleanupTasks` 把任何存在且不以当前 `storageDir` 字符串开头的 `file_path/thumb_path` 作为清理目标（`:412` 至 `:425`），删除入口随后无 ownership、realpath 或 canonical containment 校验地调度这些任务（`:4934` 至 `:4953`）。结合 D11-P0-03 的任意路径写入，攻击或异常历史数据可借“删除一篇文献”递归清空用户目录。

**落实方案：** 永久删除只允许 canonical realpath 严格位于 `data/storage/<docId>/` 内且 ownership=`managed` 的资产；比较使用路径组件 containment，不使用字符串前缀。外部 source、repository 和用户选定文件永远只解除引用，不删除。删除前由 main 生成包含每个路径/ownership/预计数量的 preview，确认时重验 inode/realpath；异常旧路径进入隔离诊断并默认跳过。故障注入覆盖目录根、父目录、相似前缀、junction/symlink、大小写和路径重定向。

### D11-P1-01 启动孤立目录清理可能删除正在导入的文献目录

**证据等级：已确认存在竞态窗口。**

主窗口显示后才调度启动恢复（`src/main/index.ts:222` 至 `src/main/index.ts:234`）。恢复会读取当前全部文献 ID，然后立即删除 `storage` 下所有不在集合中的目录（`src/main/startup-recovery.ts:556` 至 `src/main/startup-recovery.ts:574`）。正常 TXT/EPUB 导入会先创建目标目录并等待复制、解析，之后才插入文献行（`src/main/ipc/documents.ts:3979` 至 `src/main/ipc/documents.ts:4040`）。因此用户在恢复运行期间开始导入时，新目录可能暂时不在数据库中并被误删。

**落实方案：**

- 导入在创建 storage 目录前登记持久化或内存租约，恢复清理跳过所有活跃租约。
- 孤立项先移动到 `storage/.quarantine/<timestamp>/<name>`，不立即递归删除。
- 只处理早于本次启动、超过安全年龄且不属于当前/持久化任务的目录。
- 下一次成功启动并再次确认无引用后再永久删除。
- 新版并发测试让启动恢复停在清理阶段，同时启动 TXT、EPUB、PDF 和图片导入，验证源文件与目标目录均不丢失。

### D11-P1-02 备份复制的不是受验证的 SQLite 在线快照，manifest 也没有文件哈希

**证据等级：高风险推断，需故障注入验证。**

备份前只调用 `saveDatabase()`，该函数执行 `wal_checkpoint(PASSIVE)`，失败只记录日志（`src/main/database.ts:2325` 至 `src/main/database.ts:2337`）。随后 `copyCurrentDataTo` 同步递归复制整个 `db` 目录（`src/main/backup.ts:443` 至 `src/main/backup.ts:460`）。数据库、WAL 和 SHM 是分开复制的普通文件，不是同一时点的 SQLite 快照。

manifest 只记录目录文件数、总字节和外置引用数（`src/shared/backup-integrity.ts:12` 至 `src/shared/backup-integrity.ts:25`）；同尺寸损坏、数据库页损坏和内容被替换都可能不被发现。

**落实方案：**

- 使用 better-sqlite3 已有在线 backup 能力或 SQLite 原生安全快照方式生成单独数据库副本，不新增 ORM。
- 对快照执行 `quick_check`，记录 SQLite user_version、Schema 指纹和关键表计数。
- manifest v2 为数据库、配置和 storage 文件记录 SHA-256；超大文件可流式计算。
- 旧 manifest v1 继续可导入，但界面标记为“兼容校验，未包含强哈希”。
- 备份完成后随机抽样读取外置 payload；手动“验证全部文件”作为可选深度检查。

### D11-P1-03 外置大字段损坏或缺失时会静默退化为空内容

**证据等级：已确认。**

外置文件直接写到最终哈希路径（`src/main/page-payload-files.ts:86` 至 `src/main/page-payload-files.ts:102`），已有同名文件时不重写。读取只解压 JSON 并返回 `value`，没有核对文件内 `sha256` 或路径哈希（`src/main/page-payload-files.ts:105` 至 `src/main/page-payload-files.ts:114`）。`hydratePagePayloadRow` 读取失败时保留原占位字段，不返回错误（`src/main/page-payload-store.ts:107` 至 `src/main/page-payload-store.ts:118`）。

这会让 OCR、版式还原、检索、AI 证据和导出在数据损坏时表现为“没有文字”，而不是可恢复的数据完整性错误。

**落实方案：**

- 先写同目录临时文件，完成 gzip、fsync 和 SHA-256 校验后原子 rename。
- 读取时核对路径哈希、JSON 内哈希和实际内容哈希；损坏文件移入隔离区。
- hydration 返回 typed 状态：`ready | missing | corrupt | legacy-unverified`，核心调用方不能把 missing/corrupt 当作空字符串。
- 健康中心列出受影响文献、页码、字段和恢复动作，可从备份补回或重新 OCR。

### D11-P1-04 数据库诊断、备份和 VACUUM 仍会阻塞主进程

**证据等级：已确认。**

- `getDatabaseStorageDiagnostics` 会调用两次 `getPagePayloadStorageStats`，每次扫描全部 payload 文件并读取全部引用列（`src/main/database-maintenance.ts:397`、`src/main/database-maintenance.ts:516` 至 `src/main/database-maintenance.ts:527`）。
- 备份递归复制、统计目录大小和检查每个 payload 都使用同步文件 API（`src/main/backup.ts:56` 至 `src/main/backup.ts:94`、`src/main/backup.ts:242` 至 `src/main/backup.ts:267`）。
- `compactDatabase` 在主进程直接运行 `VACUUM`（`src/main/database-maintenance.ts:713` 至 `src/main/database-maintenance.ts:739`）。

超大文库允许任务耗时增长，但不能让阅读器、检索和设置页失去响应。

**落实方案：**

- 诊断、哈希、目录扫描、备份复制和深度校验移动到 worker/子进程。
- SQLite 写维护使用单一 maintenance coordinator；renderer 只订阅持久化 job 状态。
- 诊断一次扫描复用同一快照，不重复遍历。
- `VACUUM INTO` 候选文件后验证并切换，或在明确的维护窗口执行；显示阶段、预计剩余空间和取消边界。
- 所有任务设置内存上限、文件批次和可恢复游标。

### D11-P1-05 健康报告一次性生成并跨进程返回全库明细，也没有超时保证

**证据等级：已确认。**

worker 对每篇文献执行多个相关子查询，构建全部行、排序后一次性返回（`src/main/health-report-worker.ts:226` 至 `src/main/health-report-worker.ts:279`）。client 每次请求创建新 worker，没有超时和并发合并；如果 worker 以 code 0 退出但未发送结果，Promise 不会 settle（`src/main/health-report-worker-client.ts:32` 至 `src/main/health-report-worker-client.ts:70`）。

**落实方案：**

- 先返回聚合统计和报告版本；明细按严重度、类型和游标分页。
- 一个数据库只允许一个健康扫描 job；重复请求复用 job 或返回当前快照。
- 加入硬超时、取消、worker exit 无结果错误和资源上限。
- 使用分组 SQL/临时聚合替代每篇多次相关子查询，并记录真实耗时基线。

### D11-P1-06 维护状态声明“可恢复”，但没有保存真实游标，也缺少跨任务互斥

**证据等级：已确认。**

维护状态只保存阶段、剩余估计和布尔值，没有最后处理 rowid、批次 ID 或文件游标（`src/main/database-maintenance.ts:177` 至 `src/main/database-maintenance.ts:245`）。失败后再次执行会从头扫描。IPC 也没有全局 busy guard，可以同时触发清索引、外置 payload、清孤儿文件和 VACUUM（`src/main/ipc/database-maintenance.ts:29` 至 `src/main/ipc/database-maintenance.ts:80`）。

**落实方案：**

- 等待并复用模块 02/03 唯一 `task_jobs/task_items` scheduler，注册 `database-health/database-cleanup/database-compact/backup-verify` 等 maintenance kind；顶层 status、lease、heartbeat、cancel、retry 和 error 使用共享合同，不建立 `maintenance_job` 物理队列。
- `stage/cursor/result/storageLease` 作为维护领域 artifact；现有 settings JSON 在兼容期最多保存当前 jobId 和只读展示快照，不得保存 claim/lease/cursor 的第二份权威状态。共享 scheduler 未落地前，不新增“临时持久队列”来固化错误边界。
- 所有数据库/存储维护通过 scheduler 的数据库级资源令牌和互斥策略协调，读诊断可并发，写维护串行。
- 重启只从已提交的批次边界恢复，已完成批次必须幂等。

### D11-P1-07 启动恢复部分更新仍构造无界 IN 参数列表

**证据等级：已确认。**

`resetInterruptedSearchIndexJobs` 和 `reconcileCompletedOcrDocuments` 先收集全部文献 ID，再构造单个 `IN (...)` 更新（`src/main/startup-recovery.ts:93` 至 `src/main/startup-recovery.ts:110`、`src/main/startup-recovery.ts:154` 至 `src/main/startup-recovery.ts:187`）。大量中断任务可能超过 SQLite 绑定参数限制或形成很大的 SQL。

**落实方案：**

- 统一使用 100 至 500 条的 chunk helper，或直接用同一 WHERE 条件执行 set-based UPDATE。
- 启动恢复所有集合都采用游标迭代，不一次性保留全库文献 ID。
- 验收覆盖 10、1000、10 万条中断状态记录。

### D11-P2-01 诊断中的“行数”实际使用 MAX(rowid)，删除较多时会显著高估

**证据等级：已确认。**

`estimateTableRows` 返回 `MAX(rowid)`，随后写入名为 `rowCount` 的字段（`src/main/database-maintenance.ts:297` 至 `src/main/database-maintenance.ts:371`）。这适合 O(1) 规模估计，但不是实际行数，UI 和维护判断不应把它描述成精确数量。

**落实方案：** 将字段改为 `estimatedRows` 并显示“约”；关键是否存在的判断使用 bounded probe，精确计数只在 worker 中按需运行。

### D11-P2-02 存储维护错误信息仍包含乱码文本

**证据等级：已确认。**

旧索引清理失败事件和结果包含乱码字符串（`src/main/database-maintenance.ts:691` 至 `src/main/database-maintenance.ts:708`），现有 mojibake 检查没有发现它们。

**落实方案：** 修正文案并扩展乱码词典/启发式测试，覆盖 TS 模板字符串和常见 UTF-8/GBK 错译片段。

## 5. 目标架构

```text
Storage Operation Coordinator
  -> import lease
  -> OCR/payload write lease
  -> backup snapshot job
  -> restore exclusive job
  -> maintenance exclusive job
  -> orphan quarantine job

SQLite live DB
  -> online snapshot.db
  -> quick_check + schema/capability check
  -> manifest v2 + file hashes
  -> staging backup/restore directory
  -> atomic publish or automatic rollback
```

核心原则：

- 用户数据库原位兼容，默认不改表。
- 文件系统切换必须可逆，不能“先删后建”。
- 数据缺失必须显式报告，不能静默当作空文本。
- 长任务数量不限，但队列、worker、内存、并发和批次有界。
- 备份和恢复是产品核心能力，必须有真实故障注入测试，不能只依赖源码字符串断言。

## 6. 分阶段落实方案

### 阶段 A：立即数据安全护栏

- 为恢复和自动备份瘦身增加 staging、原子切换和自动回滚。
- 备份恢复失败后自动重新打开旧数据库。
- 孤立 storage 清理增加活跃导入租约、年龄阈值和 quarantine。
- 所有破坏性维护加入进程内互斥锁。

### 阶段 B：可信快照与 manifest v2

- 使用 SQLite 在线快照生成备份数据库。
- manifest 增加 app/schema/storage 版本和文件 SHA-256。
- 旧备份继续兼容导入，并显示校验级别。
- 增加“只验证，不恢复”入口。

### 阶段 C：外置 payload 完整性

- 临时文件加原子 rename。
- 读取时校验 hash，记录 missing/corrupt 状态。
- 健康中心提供文献/页级恢复列表。
- 清理只删除经过两次扫描确认的孤儿文件。

### 阶段 D：worker 化维护与可恢复任务

- 备份复制、哈希、诊断、健康报告和文件扫描进入 worker。
- 保存真实 cursor 和 heartbeat，重启从批次边界恢复。
- VACUUM/压缩进入明确维护窗口，阅读器保持可用或给出准确暂停状态。

### 阶段 E：安全边界收紧

- 文件访问 capability 化。
- 结合模块 07 的密钥脱敏和模块 12 的 Electron 威胁模型，逐步验证 sandbox、CSP 和本地协议权限。
- 安全收紧必须覆盖安装版、便携版、PDF.js、EPUB、原图和备份导入。

## 8. 新功能建议

### 8.1 数据恢复中心

集中展示最近备份、校验级别、上次恢复结果、隔离目录、缺失 payload 和可执行恢复动作。默认只显示统计，不读取或上传正文。

### 8.2 恢复预演

用户选择备份后先在 staging 中打开并生成差异预览：文献数、页数、研究项目、设置、storage 大小和缺失文件。用户确认后才执行切换。

### 8.3 定期备份演练

可选地在后台对最新槽位执行“解包、只读打开、quick_check、抽样 payload”演练，结果写入健康中心。默认本地运行，不上传任何内容。

### 8.4 数据完整性地图

按文献显示原文件、页图、OCR 文本、结构化结果、搜索索引、翻译、AI 布局、摘录和备份覆盖状态，帮助用户判断哪些数据可重建、哪些必须备份。

## 9. 依赖、迁移与审批

- 在线 SQLite 快照、SHA-256、临时目录和原子 rename 可使用现有 better-sqlite3、Node 标准库和现有 worker_threads 完成，不需要新依赖。
- 第一阶段不迁移现有数据库。
- 模块 01/03/07 的 P0 `CredentialVault` 使用 Electron 内置 `safeStorage` 和 `userData/secrets` sidecar，不属于新增“加密密钥库”依赖。普通数据库备份必须排除 sidecar，并在 manifest 标记恢复后 `credential-required`；历史含明文 protected key 的备份先生成验证过的脱敏替代副本，原件只在用户明确确认后隔离或删除。
- 若后续引入第三方跨进程文件锁库、增量备份库、压缩归档替代库、可移植密码库或云备份 SDK，必须单独评估许可证、体积、Windows 兼容、安全、离线能力和回退，并标记 **实施前需用户确认**。
- 任何新增 maintenance 表只允许旁路新增，不修改或删除现有业务表；必须先自动备份并支持旧版本忽略新表。

## 10. 与其他模块的约束

- 导入和 OCR 必须向存储协调器登记租约，不能与孤儿清理、恢复和压缩互相踩踏。
- 检索和 AI 读取外置 payload 时必须传播 missing/corrupt 状态，不能把它改成无证据的空答案。
- CredentialVault sidecar/journal 由 typed settings 服务拥有；备份模块只负责排除、manifest、恢复后的 credential-required 状态和历史备份脱敏，不复制或解密 secret。
- UI 不得把“安全副本已创建”描述成“恢复一定可回滚”，除非自动回滚已经实现并通过故障注入。
- 新版验收先于正式实现更新；数据库、备份和恢复属于发布阻断门禁。
